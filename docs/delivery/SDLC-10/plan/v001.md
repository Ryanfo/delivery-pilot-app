# Implementation plan: Add a "Starred only" filter to the task list

> Provenance is added by the coordinator. Implements the approved specification revision named in the provenance.

## Approach
Extend the existing pure query model in `src/domain/filter.ts` — the architecture's stated
extension point for new query features — rather than adding ad-hoc filtering in `App.tsx`.
`TaskQuery` gains two required fields: `starredOnly: boolean` and `starredIds: ReadonlySet<string>`.
`filterTasks` applies both the existing status predicate and, when `starredOnly` is true, a
membership test against `starredIds`, combined with logical AND. The starred ID set already
lives as React state (`starred`) in `App`, loaded via `src/storage/starred.ts`; it is passed
into the query as plain data, so `src/domain/` stays free of I/O as the specification requires.

In `App.tsx`, a new `starredOnly` boolean state (default `false`) drives a checkbox rendered
in the existing `.controls` block, next to the status `<select>`, using the same
label-with-`htmlFor`/`id` pattern already used for "Status" — no new CSS. The checkbox is a
native `<input type="checkbox">`, which is keyboard operable (Tab to focus, Space to toggle)
with no extra handling needed. `visible` (the `useMemo`-derived list passed to `TaskList`) is
recomputed from `filterTasks(tasks, { status, starredOnly, starredIds: starred })`, so the
"Showing X of Y tasks" count, the existing empty-state message in `TaskList`, and the list's
reactivity to `toggleStar` all pick up the combined filter automatically — no changes are
needed to `TaskList.tsx` or the empty-state message.

No new runtime dependencies, no persistence of the checkbox state, and no change to how
starring itself works.

## Interfaces and data
`src/domain/filter.ts`:
```ts
export interface TaskQuery {
  readonly status: StatusFilter;
  readonly starredOnly: boolean;
  readonly starredIds: ReadonlySet<string>;
}

export function filterTasks(tasks: readonly Task[], query: TaskQuery): Task[] {
  return tasks.filter(
    (task) =>
      (query.status === "all" || task.status === query.status) &&
      (!query.starredOnly || query.starredIds.has(task.id)),
  );
}
```
`TaskQuery` is a breaking change to an internal (non-exported-package) interface: its two
call sites, `src/App.tsx` and `src/domain/filter.test.ts`, are both updated in this change.
No storage format, schema, or external dependency changes. `sortTasks` is unchanged.

## Implementation steps
1. In `src/domain/filter.ts`, add `starredOnly: boolean` and `starredIds: ReadonlySet<string>`
   to `TaskQuery`, and update `filterTasks` to AND the existing status predicate with
   `!query.starredOnly || query.starredIds.has(task.id)`. Keep the function pure (no
   mutation of `tasks` or `starredIds`).
2. In `src/domain/filter.test.ts`, update the three existing `filterTasks` test calls to pass
   `starredOnly: false, starredIds: new Set()` alongside `status`. Add new cases: filtering to
   starred tasks only when `starredOnly` is true; combining `status` and `starredOnly`
   (logical AND, e.g. `in_progress` + starred); and an empty result when `starredOnly` is true
   and `starredIds` is empty — each without mutating the input array.
3. In `src/App.tsx`, add `const [starredOnly, setStarredOnly] = useState(false);`. Update the
   `visible` `useMemo` to call `filterTasks(tasks, { status, starredOnly, starredIds: starred })`
   with `starredOnly` and `starred` added to its dependency array. Render a checkbox in the
   `.controls` div, after the status control: a `<label htmlFor="starred-only-filter">Starred
   only</label>` and `<input id="starred-only-filter" type="checkbox" checked={starredOnly}
   onChange={(e) => setStarredOnly(e.target.checked)} />`, matching the existing label/control
   pairing style used for "Status". Leave `TaskList`, the empty-state message and the
   "Showing X of Y tasks" line untouched; they already derive from `visible`.
4. In `src/App.test.tsx`, add tests: (a) the checkbox is present, labelled "Starred only" and
   unticked on initial render (AC1); (b) ticking it (via `userEvent.click`) narrows the list to
   only starred tasks, using `tasks` and `store` props to set up a known starred task (AC2);
   (c) ticking it together with selecting a status narrows to tasks matching both (AC3); (d)
   with `starredOnly` ticked, clicking "Unstar" on a visible task removes it from the list
   without any other interaction (AC4); (e) ticking it when no starred task matches the current
   status shows `screen.getByRole("status")` with "No tasks match the current filter." (AC5);
   (f) the "Showing X of Y tasks" text's X updates to the combined-filter count while Y stays
   at the total (AC6); (g) focusing the checkbox and pressing Space toggles it, confirmed via
   `aria-checked`/`checked` state or the resulting filtered list (AC7, keyboard).
5. In `e2e/app.spec.ts`, extend the existing journey (or add a new `test(...)`): star a second
   task, tick "Starred only" (`page.getByLabel("Starred only").check()`), assert the task list
   shows only starred tasks, combine with the status filter to assert the AND behaviour, then
   untick it and assert the full list returns. Keep the existing reload/persistence assertions
   for starring unchanged.
6. Run `npm run lint`, `npm run typecheck`, `npm run test:unit`, `npm run build` and
   `npm run test:e2e` locally; fix any failures before handing off (AC7).

## Risks
| Risk | Mitigation |
|---|---|
| Widening `TaskQuery` to required fields breaks any other caller not covered by this plan | Repo-wide search confirms `filterTasks`/`TaskQuery` has exactly two call sites (`src/App.tsx`, `src/domain/filter.test.ts`); both are updated in this change |
| A Testing Library query for the new checkbox could ambiguously match if label text overlaps other content | "Starred only" is a distinct string not used elsewhere in the rendered output; use `getByLabelText("Starred only")` / `getByRole("checkbox", { name: "Starred only" })` for an unambiguous, role-scoped query |
| Forgetting to add `starredOnly`/`starred` to the `useMemo` dependency array would make the list stale when toggling the checkbox or unstarring (regressing AC4) | Explicit dependency array update is step 3; the AC4 test exercises exactly this path and would fail if the dependency were missing |

## Rollback implications
No persisted state, storage schema or migration is introduced (the checkbox state is
in-memory `App` state only, not saved to `src/storage/starred.ts`). Reverting is a single
commit revert of the five modified files; no data cleanup is required.
