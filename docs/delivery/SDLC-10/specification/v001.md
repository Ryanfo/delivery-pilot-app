# Specification: Add a "Starred only" filter to the task list

> Provenance (ticket, revision, run, inputs) is added by the coordinator on publication.

## Problem and outcome
People star the tasks they care about but currently have no way to see only those tasks; they must scan the whole list to find starred items. The outcome is a "Starred only" checkbox that, when ticked, narrows the visible task list to starred tasks, usable together with the existing status filter.

## Scope
- In scope:
  - A "Starred only" checkbox control next to the existing status filter, unticked by default.
  - Filtering the visible task list to starred tasks only when the checkbox is ticked.
  - Combining the "Starred only" filter with the existing status filter (logical AND).
  - Keeping the list reactive: unstarring a task while "Starred only" is ticked removes it from the visible list immediately.
  - Reusing the existing empty-state message when the combined filters match no tasks.
  - The "Showing X of Y tasks" count reflecting the filtered (X) list; this already changes based on filters.
  - Extending the pure filtering logic in `src/domain/filter.ts` (per `docs/architecture.md`: "New query features extend `TaskQuery` ... rather than adding ad-hoc filtering in components") with unit tests covering the new behaviour, including combined-filter cases.
  - Extending the Playwright end-to-end test (`e2e/app.spec.ts`) to cover the new filter.
  - Keyboard operability of the new checkbox.
- Out of scope (see Exclusions).

## Exclusions
- Persisting/remembering the "Starred only" checkbox state between visits (it always starts unticked).
- Any change to how starring itself works (the star/unstar button, its labelling, or `src/storage/starred.ts`).
- New runtime dependencies.
- Visual redesign beyond matching the existing control styles.

## Acceptance criteria
- **AC1**: A "Starred only" checkbox with a visible, associated label appears next to the existing status filter control and is unticked by default on load.
- **AC2**: When "Starred only" is ticked, the task list shows only tasks that are starred.
- **AC3**: "Starred only" and the status filter apply together (for example, "In progress" status + "Starred only" shows only starred tasks that are also in progress).
- **AC4**: While "Starred only" is ticked, unstarring a task removes it from the visible list immediately, without requiring a reload or other filter change.
- **AC5**: When the combined filters (status + "Starred only") match no tasks, the existing "No tasks match the current filter." message (`role="status"`) is shown, unchanged.
- **AC6**: The "Showing X of Y tasks" line's X counts the list after both the status filter and the "Starred only" filter are applied; Y continues to reflect the total task count as it does today.
- **AC7**: The "Starred only" checkbox is operable by keyboard (focusable and toggled with the keyboard, e.g. Space), and all configured checks pass: lint, typecheck, unit, build, e2e.

## Non-functional requirements
- Accessibility: the checkbox must have a visible, programmatically associated label (per `docs/coding-standards.md`) and be keyboard-operable (AC7); list updates continue to use the existing `aria-live` region / `role="status"` empty state pattern already in `App.tsx` and `TaskList.tsx`.
- No new runtime dependencies (per `docs/guardrails.md` and the brief's exclusions).
- Consistency: visual styling of the new checkbox should match existing controls in the `.controls` section; no redesign.

## Constraints
- Client-only React + TypeScript SPA (Vite), no backend, no network calls (`docs/architecture.md`).
- TypeScript `strict`, no `any`, no non-null assertions, small/named/pure functions in `src/domain/` (`docs/coding-standards.md`).
- Filtering logic must stay a pure function in `src/domain/` per the architecture's stated convention for new query features (extend `TaskQuery`), not ad-hoc filtering inside components.
- Each acceptance criterion must map to at least one named test (`docs/testing-policy.md`); existing tests must not be weakened, skipped or deleted.
- Starring state (`starred: Set<string>`) currently lives in `App.tsx` React state, loaded/saved via `src/storage/starred.ts`; the pure filter function in `src/domain/filter.ts` does not currently have access to this set, so the new query logic needs the starred set (or equivalent) passed in as data, not read from storage directly — this keeps `src/domain/` free of I/O. Exact signature is a plan-stage decision.

## Designs and attachments
None.

## Dependencies
- Existing status filter (`StatusFilter`, `src/domain/filter.ts`) and its UI in `src/App.tsx`, which the new checkbox sits next to and combines with.
- Existing starred-state management (`starred` Set, `toggleStar`) in `src/App.tsx`, which the new filter reads but does not modify.
- Existing empty-state message and "Showing X of Y tasks" line in `src/App.tsx`, which must continue to work unchanged under the combined filters.

## Assumptions
- The checkbox's visible label text is "Starred only", matching the ticket's own naming of the feature; exact wording is not otherwise specified and is not material to acceptance.
- The checkbox is placed in the existing `.controls` section alongside the status `<select>`, consistent with "next to the existing status filter" in the brief.
- "Y" in "Showing X of Y tasks" continues to mean the total number of tasks passed into `App` (unaffected by either filter), matching current behaviour; only "X" (the filtered count) is required to reflect both filters (AC6).
- Keyboard operation for a checkbox means standard browser checkbox behaviour (Tab to focus, Space to toggle); no custom key handling is implied.
