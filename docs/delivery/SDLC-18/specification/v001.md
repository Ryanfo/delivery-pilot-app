# Specification: Update status of items

> Provenance (ticket, revision, run, inputs) is added by the coordinator on publication.

## Problem and outcome
The task list app shows each task's status ("To do", "In progress" or "Done") as read-only
text in the task's meta line (`src/components/TaskList.tsx`). Users can filter by status,
star tasks and search by title, but they cannot change a task's status: statuses come only
from the checked-in fixture data in `src/data/tasks.ts`, and `Task.status` is read-only.

After this change, a user can change the status of any task from the task list, using a
labelled, keyboard-operable control on that task. The new status shows straight away
everywhere the app uses status: the task's displayed status, the status filter, and the
"Showing X of Y tasks" count.

The brief says "ticket"; in this app the items are called tasks, so this specification uses
"task" throughout.

Whether a changed status survives a page reload (as stars already do) is not settled by the
brief and is asked as **Q1**. The criteria below are written for the proposed default
(the status persists in browser storage); AC6 and AC7 change or drop if the answer is
"no".

## Scope
- In scope:
  - A per-task control in the task list for changing that task's status to any of the three
    existing statuses (`todo`, `in_progress`, `done`, shown as "To do", "In progress",
    "Done").
  - The task list, status filter and results count reflecting the changed status
    immediately.
  - (Pending Q1, proposed default) Saving changed statuses in browser storage, through the
    existing `KeyValueStore` persistence boundary, so they survive a reload; corrupt,
    missing or unavailable storage falls back to the fixture statuses without breaking the
    page.
  - Unit, component and end-to-end tests per `docs/testing-policy.md`.

## Exclusions
- Out of scope:
  - Editing any other task field (title, description, priority, due date).
  - Creating, deleting or reordering tasks (the list keeps its priority/title sort).
  - New statuses or a configurable status set; workflow rules restricting which status
    can follow which.
  - Bulk status changes across several tasks.
  - A backend, network calls or syncing between browsers/devices (the app is client-only).
  - Change history, undo, or timestamps for status changes.
  - Changing the fixture data in `src/data/tasks.ts`.
  - Changes to starring, search or the existing filters beyond reflecting the new status.

## Acceptance criteria
- **AC1**: Given the task list is shown, when the user looks at any task, then the task has
  a status control whose accessible name identifies the task (for example
  "Status for Draft onboarding checklist"), offering exactly "To do", "In progress" and
  "Done", with the task's current status selected.
- **AC2**: Given a task with status "To do", when the user changes its status to
  "In progress" with the control, then that task's displayed status reads "In progress"
  without a page reload, and no other task's status changes.
- **AC3**: Given the status filter is "All", when the user changes a task's status, then the
  task stays in the list in the same position (the sort order does not depend on status) and
  the "Showing X of Y tasks" count is unchanged.
- **AC4**: Given the status filter is set to a status (for example "To do"), when the user
  changes a visible task to a different status, then the task leaves the list immediately,
  the "Showing X of Y tasks" count drops by one, and if no tasks remain the existing
  "No tasks match the current filter." message is shown. Selecting the task's new status in
  the filter shows it again.
- **AC5**: Given keyboard-only use, when the user tabs to a task's status control and changes
  the value with the keyboard, then the status changes as in AC2; the control has a visible
  focus indicator.
- **AC6** (pending Q1): Given the user has changed one or more task statuses, when the page
  is reloaded, then those tasks show the statuses the user set, and tasks the user did not
  change show their fixture status.
- **AC7** (pending Q1): Given browser storage holds corrupt or unreadable status data, or
  storage is unavailable or full, when the app loads or a status is changed, then the page
  still renders, tasks show their fixture status (or the in-session change), and no error
  reaches the user.
- **AC8**: Given the change is in place, then starring, the "Starred only" filter, search,
  the status filter and the results count behave as before, combined with changed statuses,
  and every acceptance criterion maps to at least one named test (unit for domain/storage
  functions, component for user-visible behaviour, and the end-to-end journey covers
  changing a status).

## Non-functional requirements
- Accessibility (`docs/coding-standards.md`): each status control has a visible or
  programmatically associated label unique to its task, is keyboard operable, and the
  results-count `aria-live` region continues to announce count changes. Text and control
  colours meet the contrast checks already enforced by `e2e/styling.spec.ts`.
- Performance: changing a status updates the list without noticeable delay for the fixture
  size (12 tasks); no change to load behaviour.
- Security/privacy: synthetic data only; nothing leaves the browser.
- Compatibility: works in the browsers already covered by the Playwright configuration.

## Constraints
- Client-only React + TypeScript app; state lives in `App`, derived lists come from pure
  domain functions (`docs/architecture.md`). Status filtering stays in `filterTasks` /
  `TaskQuery` in `src/domain/filter.ts`.
- Persistence, if kept (Q1), goes through the storage boundary in `src/storage/` and must be
  resilient to corrupt or missing data, like `task-list:starred:v1`.
- TypeScript strict rules, stable task IDs as keys, no lint/type suppressions
  (`docs/coding-standards.md`).
- No new runtime dependencies without an explicit plan decision; do not modify `.github/`,
  `CLAUDE.md`, `.claude/` or `docs/delivery/` (`docs/guardrails.md`).
- The form of the control (native select, button group, menu) and the storage format are
  plan decisions, within AC1 and AC5.

- No other tickets are linked.

## Assumptions
- "Ticket" in the brief means a task in this app's task list.
- Any status can be changed to any other status; there are no transition rules.
- The control sits on each task in the list (inline), not in a separate detail view or
  dialog, since the app has no detail view.
- Under an active status filter, a task whose new status no longer matches leaves the list
  immediately (AC4), consistent with how unstarring behaves under "Starred only" today.
  See Q2.
- Status changes apply to tasks supplied to `App` by ID; a stored status for an ID that is
  not in the current task list is ignored.
- No confirmation step is needed before changing a status.

## Open questions
- **Q1**: Should a changed status persist across page reloads (saved in browser storage
  like stars), or only last until the page is reloaded? (Material: it decides whether AC6
  and AC7 and the storage work are in scope. Proposed default: persist, matching how stars
  already behave.)
- **Q2**: When a status filter is active and the user changes a task to a status outside
  that filter, should the task disappear from the list immediately (proposed, matching the
  "Starred only" behaviour), or stay visible until the filter changes? (Not material: it
  only adjusts AC4; the proposed behaviour is assumed unless told otherwise.)
