# Implementation plan: Update status of items

> Provenance is added by the coordinator. Implements the approved specification revision named in the provenance.

Implements specification v003 (SDLC-18-SPEC-v3). No designs or attachments were provided.

## Approach
Keep the fixture data unchanged and hold the user's status changes as a map
`task ID → TaskStatus` in `App` state. This works the same way as `starred` and follows `docs/architecture.md`
(state in `App`, derived lists from pure domain functions):

- **Domain**: a pure function `withStatuses(tasks, overrides)` returns the tasks with any
  overridden status applied. It ignores override IDs that are not in `tasks` (AC7). `App` runs
  `filterTasks` / `sortTasks` on this derived list, so the displayed status, status filter and results count all
  read the same status (AC2–AC4, AC6). `TaskQuery` and `filterTasks` do not change. Sorting is by
  priority/title/ID, so a task keeps its position when its status changes (AC3).
- **Storage**: a new module `src/storage/statuses.ts` sits behind the existing `KeyValueStore`
  boundary. It has its own key, `task-list:status:v1`, and stores a JSON object
  `{"<taskId>": "<status>"}` with keys sorted. Like `loadStarred`, loading never throws. Corrupt JSON, a value that is not an object,
  unreadable storage or no storage all give an empty map, and entries with an invalid status
  value are dropped. Saving returns `false` when `setItem` throws (quota or denied). The stars key
  (`task-list:starred:v1`) and its format stay as they are.
- **UI control**: a native `<select>` on each task, offering "To do", "In progress" and "Done". A native
  select works with the keyboard and screen readers without extra code (AC1, AC5), and needs
  no new dependency. Its `<label>` shows "Status" and has a visually hidden
  " for {title}" suffix. The accessible name is then unique per task ("Status for Draft onboarding
  checklist") and the label stays visible, as `docs/coding-standards.md` requires. The read-only status text in
  `.task-meta` stays, so the displayed status and the control both show the current value (AC2 and AC6
  name them separately).
- **Placement**: the control goes in a new `.task-actions` row, **after** the star button.
  Tab order stays status filter → Starred only → Search → first star, which the existing
  styling test AC9 relies on. The status control comes next in tab order.

No architectural decision needs an ADR. The control form and the storage key/format are
the plan decisions the specification left open. They are recorded above.

## Interfaces and data
- `src/domain/task.ts`
  - `export const TASK_STATUSES: readonly TaskStatus[] = ["todo", "in_progress", "done"]`
  - `export function isTaskStatus(value: unknown): value is TaskStatus`
  - `export function withStatuses(tasks: readonly Task[], overrides: ReadonlyMap<string, TaskStatus>): Task[]`
    creates new objects (`{ ...task, status }`) only for overridden tasks. It never mutates its input and keeps the input
    order.
- `src/storage/statuses.ts`
  - `export const STATUS_KEY = "task-list:status:v1"`
  - `export function loadStatuses(store: KeyValueStore | undefined): Map<string, TaskStatus>`
  - `export function saveStatuses(store: KeyValueStore | undefined, statuses: ReadonlyMap<string, TaskStatus>): boolean`
  - Reuses `KeyValueStore` imported from `./starred`. The interface is not moved, to avoid churn.
- Storage format: `localStorage["task-list:status:v1"] = '{"t-001":"in_progress","t-004":"todo"}'`.
  It holds only the tasks the user changed. Setting a task back to its fixture status is stored like any other
  change (spec assumption).
- `TaskList` props: adds `readonly onChangeStatus: (id: string, status: TaskStatus) => void`.
- Control DOM per task: `<label for="task-status-{id}">Status<span class="visually-hidden"> for {title}</span></label>
  <select id="task-status-{id}">` with options `todo` / `in_progress` / `done`, labelled from `STATUS_LABELS`.
  The `onChange` handler narrows with `isTaskStatus`, so no cast is needed (like `isStatusFilter` in `App`).

## Implementation steps
1. **Domain**: add `TASK_STATUSES`, `isTaskStatus` and `withStatuses` to `src/domain/task.ts`, with
   `src/domain/task.test.ts` (empty overrides, unknown ID ignored, no mutation, order preserved,
   `isTaskStatus` rejects `"blocked"`, `""`, `null`, `1`).
2. **Storage**: add `src/storage/statuses.ts` and `src/storage/statuses.test.ts` (round-trip with sorted
   keys; corrupt JSON, array, `null`, string → empty; invalid status values dropped while valid
   entries are kept; throwing `getItem`/`setItem` and `undefined` store; saving does not touch
   `STARRED_KEY`).
3. **TaskList**: add the `.task-actions` row with the star button (unchanged), then the labelled status
   select bound to `task.status` and calling `onChangeStatus(task.id, value)`.
4. **App**: `const [statuses, setStatuses] = useState(() => loadStatuses(store))`;
   `const current = useMemo(() => withStatuses(tasks, statuses), [tasks, statuses])`. Run filtering and sorting
   on `current`. The results line keeps `tasks.length` for Y. Add `changeStatus(id, status)`, which builds a new
   Map and calls `saveStatuses` the same way `toggleStar` saves stars. Its failure result is ignored, so no error reaches the
   user (AC7).
5. **Styles**: `.task-actions { display: flex; flex-wrap: wrap; align-items: center; gap: … }`. The task
   status label uses the existing kicker treatment (muted, uppercase, letter-spaced, `--font-kicker`).
   Add a standard `.visually-hidden` clip rule. The control picks up the existing `select` field styling and
   `select:focus-visible` accent outline (AC5). Check it fits without horizontal scroll at 320px.
6. **Component tests** in `src/App.test.tsx` (see mapping).
7. **E2E**: update `getByLabel("Status")` → `getByLabel("Status", { exact: true })` in `e2e/app.spec.ts` and
   `controls()` in `e2e/styling.spec.ts`. Playwright's `getByLabel` matches substrings by default, so
   "Status for …" would otherwise make those locators ambiguous. This change only disambiguates the locators; it does not weaken any assertion.
   Add the status journey test and extend the styling checks.
8. Run `npm run lint`, `npm run typecheck`, `npm run test:unit`, `npm run build`, `npm run test:e2e`.

## Risks
| Risk | Mitigation |
|---|---|
| Existing Playwright `getByLabel("Status")` becomes ambiguous (substring match on "Status for …") and existing e2e tests fail in strict mode | Use `{ exact: true }` on those locators (step 7). Testing Library's `getByLabelText("Status")` is already exact, so the component tests are unaffected |
| New focusable control changes tab order and breaks styling AC9 | Put the control after the star button; extend AC9 instead of reordering it |
| Styling AC4 counts exactly 14 kicker elements (`.controls` labels + `.task-meta`) | Do not add new `.task-meta` elements or `label[for="status-filter"]`-style labels inside `.controls`; the task status label lives in `.task-actions` |
| New select inherits kicker uppercase or shrinks below readable size, or overflows at 320px | It uses the existing `select` rule (`font: inherit` from `.task-actions`, body font); the extended AC10/AC11 checks cover contrast and fit |
| Storage write fails (quota/denied) | `saveStatuses` catches and returns `false`; in-session state still updates (AC7) |
| Stored statuses for removed tasks pile up | Harmless and ignored at render (`withStatuses`); pruning is out of scope |

## Rollback implications
Revert the change. The only lasting data is the `task-list:status:v1` localStorage entry. After a revert
the old code never reads it, so tasks show fixture statuses again. Stars use a separate, unchanged key and
are unaffected. No migrations.
