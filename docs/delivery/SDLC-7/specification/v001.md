# Specification: Add a "HELLO WORLD" welcome block to the task list page

> Provenance (ticket, revision, run, inputs) is added by the coordinator on publication.

## Problem and outcome
The task list page (`src/App.tsx`) currently has no welcome message. The delivery pipeline
needs a simple, highly visible copy block on the page so that changes pushed through the
pipeline can be confirmed as reaching the running app. After this change, anyone loading the
app sees a block containing the exact text "HELLO WORLD" between the "Task list" heading and
the status filter, and screen reader users are told what the block is via an accessible name.

## Scope
- In scope:
  - A static copy block in `src/App.tsx`, positioned directly below the `<h1>Task list</h1>`
    heading and above the status filter controls.
  - The block's visible text is exactly `HELLO WORLD` (all capitals, no additional copy).
  - The block is a semantic element with an accessible name so assistive technology announces
    it (for example a `<section>` with an `aria-label`, or an equivalent accessible pattern).
  - A unit test asserting the block renders with the exact text "HELLO WORLD".
  - An update to the existing Playwright end-to-end test (`e2e/app.spec.ts`) asserting the
    block is visible when the app loads.

- Out of scope (see Exclusions).

## Exclusions
- Styling beyond what the existing stylesheet already provides (no new CSS rules or classes
  for visual treatment).
- Translations or localisation of the text.
- Making the text configurable (no props, settings or data source for the copy).
- Any change to task data, filtering behaviour, or starring behaviour.

## Acceptance criteria
- **AC1**: The main page shows the text "HELLO WORLD" directly below the "Task list" heading.
- **AC2**: The block is a semantic element (for example a `<section>` with an accessible name)
  so screen readers announce it.
- **AC3**: A unit test confirms the block renders with the exact text "HELLO WORLD".
- **AC4**: The existing end-to-end test confirms the block is visible when the app loads.
- **AC5**: Existing behaviour is unchanged: filtering, starring and the task count work as
  before, and all configured checks (lint, typecheck, unit, build, e2e) pass.

## Non-functional requirements
- Accessibility: the block must have a visible, non-empty accessible name per
  `docs/coding-standards.md`, consistent with the rest of the app's accessible-control pattern.
- No new runtime dependencies (per `docs/guardrails.md`); the block uses existing React/HTML
  only.
- No change to app performance characteristics expected; this is a small static addition.

## Constraints
- Implementation must follow `docs/coding-standards.md`: TypeScript strict mode, no `any`,
  components stay thin, no blanket lint/type suppressions.
- Must not modify `.github/`, `CLAUDE.md`, `.claude/` or `docs/delivery/` (per
  `docs/guardrails.md`).
- Placement is fixed: between the `<h1>` heading and the `<div className="controls">` status
  filter block in `src/App.tsx`.
- Choice of exact HTML tag, accessible-name technique (e.g. `aria-label` vs. visually
  hidden heading), and test selector/query are implementation decisions for the plan stage,
  within the constraint that the element is semantic and has an accessible name.

## Dependencies
- Depends on the current structure of `src/App.tsx` (heading, controls, `TaskList`) and the
  existing test suites `src/App.test.tsx` and `e2e/app.spec.ts`, which this change extends
  without altering their existing assertions.

## Assumptions
- The accessible name of the new element does not need to be a specific string; any
  non-empty, descriptive accessible name (e.g. "Welcome" or the block's own text) satisfies
  AC2, since the brief does not mandate specific wording for the accessible name.
- The unit test is added to `src/App.test.tsx` (the existing App test file) rather than a new
  file, consistent with existing project structure; the plan stage may adjust this.
- No change to `docs/architecture.md`'s UI layer description is required, since this is a
  small addition within the existing `src/App.tsx` component rather than a new architectural
  layer.

## Open questions
None. The brief defines placement, exact text, element semantics, and required tests
unambiguously; remaining choices (exact tag, accessible-name string, test file layout) are
non-material implementation details left to the plan stage.
