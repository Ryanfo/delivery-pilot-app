# Specification: Search tasks by title

> Provenance (ticket, revision, run, inputs) is added by the coordinator on publication.

## Problem and outcome
As the task list grows, it takes too long to find a particular task because there is no way
to search. Users need a search box with the existing filter controls so that, as they type,
the list narrows to the tasks whose title contains the typed text. This works together with
the existing Status and "Starred only" filters.

### Current behaviour (at `be71a8c`)
- `src/App.tsx` renders a `.controls` row with a "Status" `<select>` (All / To do / In progress /
  Done) and a "Starred only" checkbox. Each control has a visible, associated `<label>`.
- The visible list is `sortTasks(filterTasks(tasks, { status, starredOnly, starredIds }))`.
  `filterTasks` and the `TaskQuery` type live in `src/domain/filter.ts`. Sorting is by priority
  (high first), then title, then ID.
- A polite live region reads `Showing {visible} of {total} tasks · {starred} starred`.
- When the visible list is empty, `TaskList` shows `No tasks match the current filter.` with
  `role="status"`.
- Filter state is held in React state and is not persisted. Only starred IDs are persisted.

## Scope
- In scope:
  - A text input labelled "Search" in the existing filter controls row.
  - Live, case-insensitive filtering on the task **title** that ignores leading and trailing spaces.
  - Combining search with the existing Status and "Starred only" filters (logical AND).
  - The existing count line and empty-state message reflecting the search.

## Exclusions
- Out of scope: searching task descriptions (or any field other than the title).
- Out of scope: remembering the search between visits (no persistence, and no URL state).
- Out of scope: highlighting the matched text.
- Out of scope: changes to sort order, to the Status or "Starred only" behaviour, or to starred persistence.

## Acceptance criteria
- **AC1**: Given the task list page, when it loads, then a text input with the visible,
  associated label "Search" appears in the same controls row as the existing "Status" and
  "Starred only" controls. It starts empty, so all tasks allowed by the other filters are shown.
- **AC2**: Given tasks are listed, when the user types in the Search box, then the list
  updates as they type, without a submit action, to show only the tasks whose title contains the
  search text. The match ignores upper and lower case, and leading and trailing spaces in the
  search text are ignored. For example, with the fixture data, `  ROTA ` shows only "Update support rota".
- **AC3**: Given a search term, a Status selection and/or "Starred only" are active, when the
  list is shown, then a task appears only if it matches every active filter: its title
  contains the search text, its status matches the selected Status (or Status is "All"), and
  it is starred (when "Starred only" is checked). Changing any one filter keeps the others in effect.
- **AC4**: Given a search is active, when the list updates, then the line
  "Showing X of Y tasks" reports X as the number of tasks currently visible after all filters,
  including search. Y stays the total number of tasks, and the "· N starred" part keeps
  reporting the total starred count. The line stays in the existing polite live region.
- **AC5**: Given a search, combined with the other filters, that no task matches, when the
  list updates, then the existing "No tasks match the current filter." message is shown in
  place of the list, and the count line reads "Showing 0 of Y tasks".
- **AC6**: Given a search is active, when the user clears the Search box (or leaves only
  spaces in it), then search no longer restricts the list. The tasks allowed by the
  current Status and "Starred only" filters are shown again, and the count updates to match.

## Non-functional requirements
- Accessibility: the Search input has a visible label associated with the control. It is
  reachable and usable by keyboard in the normal tab order alongside the other controls. Result
  changes are announced through the existing `aria-live="polite"` count line and the
  `role="status"` empty message. No new announcement mechanism is required.
- Performance: filtering happens client-side on each keystroke over the in-memory list, with
  no noticeable delay for the fixture data. No debounce is required.
- Security and privacy: no network calls. The search text is not stored or sent anywhere.
- Compatibility: behaves the same in the browsers covered by the existing Playwright setup.

## Constraints
- Client-only React + TypeScript app (Vite). No backend.
- Per `docs/architecture.md`, new query features extend `TaskQuery` in `src/domain/filter.ts`
  instead of adding filtering inside components. Domain functions stay pure.
- Per `docs/coding-standards.md`: strict TypeScript, no `any` or non-null assertions, and
  every control has a visible associated label.
- Per `docs/testing-policy.md`: unit tests for the domain filter (including empty input, case
  handling and combined filters), component tests through roles and labels (including keyboard
  use) and an end-to-end journey. Each AC maps to at least one named test.
- Per `docs/guardrails.md`: no new runtime dependencies without a plan decision. Synthetic data only.

## Designs and attachments
None. The ticket has no attachments or Figma designs, so layout follows the existing controls row.

## Dependencies
- Existing Status filter and "Starred only" filter (SDLC-10), the count line, and the
  `TaskList` empty-state message, all in the current `main` (`be71a8c`).
- No other in-flight tickets were reported as related work.

## Assumptions
- **A1**: "Contains" means a plain substring match on the title, not a word, prefix or fuzzy
  match. Spaces *inside* the search text are kept and must match literally.
- **A2**: Case is ignored using standard JavaScript lower-casing of both title and search text. No
  accent folding or other locale normalisation is applied.
- **A3**: A search that is empty or only spaces does not filter (consistent with AC2 trimming and AC6).
- **A4**: The Search input is placed after the existing controls in the same row. No placeholder
  text is required. Either `type="text"` or `type="search"` is acceptable, provided it is
  exposed as a text input labelled "Search".
- **A5**: The search starts empty on every page load (follows from "remembering the search
  between visits" being out of scope).
- **A6**: Sort order of the visible tasks is unchanged by searching.

## Original brief
**Summary:** Search tasks by title

**Description:**

With a growing list it takes a while to find a particular task; there is no way to search.
Scope: add a search box to the filter controls above the task list. As you type, the list shows only the tasks whose title contains what you typed.
Acceptance criteria
- AC1: A text input labelled "Search" appears with the existing Status and Starred only controls.
- AC2: Typing filters the list to tasks whose title contains the text, ignoring upper and lower case. Spaces at the start or end of the search are ignored.
- AC3: Search combines with the Status and Starred only filters: a task is shown only if it matches all of them.
- AC4: The "Showing X of Y tasks" line counts only the tasks the search leaves visible.
- AC5: When nothing matches, the existing "No tasks match the current filter." message is shown.
- AC6: Clearing the search box shows the tasks again.
Out of scope: searching task descriptions, remembering the search between visits, highlighting the matched text.
