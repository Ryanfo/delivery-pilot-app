# Implementation plan: Search tasks by title

> Provenance is added by the coordinator. Implements the approved specification revision named in the provenance.

## Approach
Extend the domain query rather than filtering in the component, as `docs/architecture.md` requires.

- **Domain:** add an optional `search` field to `TaskQuery` in `src/domain/filter.ts`. `filterTasks`
  trims the search text and lower-cases it once per call. A task passes the search
  clause when that normalised text is empty, or when `task.title.toLowerCase()` contains it.
  The clause is ANDed with the existing status and starred clauses. Search stays a plain
  substring match on the title only (A1, A2). Spaces inside the text are kept, and descriptions
  are never searched. An empty or all-space search does not filter (A3). `sortTasks` is unchanged,
  so sort order is unaffected (A6).
- **UI:** `App` holds `search` in React state, initialised to `""`, with no persistence (A5). It renders a
  labelled `<input type="text">` after the "Starred only" checkbox inside the existing
  `.controls` row (A4) and passes `search` into the existing `filterTasks` call in `useMemo`.
  The existing count line (`visible.length`, `tasks.length`, `starred.size`) and the `TaskList`
  empty state already use the filtered list, so AC4 and AC5 need no changes to those elements.

**Why optional `search`:** a required field would force changes to every existing `TaskQuery`
literal in `src/domain/filter.test.ts`. Making it optional keeps the existing tests unchanged and
gives the same result, because a missing value behaves exactly like `""`. `exactOptionalPropertyTypes` is satisfied
because `App` always passes a `string`.

**Why `type="text"`:** it exposes the input with role `textbox` named "Search", which matches
the spec's wording "text input labelled Search". `type="search"` would expose the role as
`searchbox` and add a browser-specific clear button. A4 allows either, and this plan
chooses `text`.

No new dependencies, storage keys, schemas or migrations. No architectural decision record is needed.

## Interfaces and data
- `TaskQuery` (exported from `src/domain/filter.ts`) gains
  `readonly search?: string;`, documented as "Title substring, matched case-insensitively after
  trimming. Empty or blank matches every task." This change is additive and backwards compatible: existing callers
  that leave out `search` behave as before.
- `filterTasks(tasks, query)` keeps the same signature and stays pure, without mutating its input. Its behaviour changes only when
  `query.search` is a non-blank string.
- `App` props (`tasks`, `store`) are unchanged. No storage format change: the search text is never
  written to `KeyValueStore` or sent anywhere.

## Implementation steps
1. **Domain (`src/domain/filter.ts`):**
   - Add `readonly search?: string;` to `TaskQuery` with a one-line doc comment.
   - In `filterTasks`, compute `const needle = (query.search ?? "").trim().toLowerCase();` before
     `tasks.filter(...)`, then add the clause
     `&& (needle === "" || task.title.toLowerCase().includes(needle))`.
2. **Domain tests (`src/domain/filter.test.ts`):** in `describe("filterTasks")`, add:
   - `"matches the title case-insensitively and ignores surrounding spaces"`: search
     `"  ROTA "` returns only `t-004` ("Update support rota").
   - `"does not filter when the search is empty or only spaces"`: `""` and `"   "` each return
     all `TASKS.length` tasks.
   - `"matches the title only, not the description"`: search `"draft"` returns only `t-001`.
     `t-002`'s description contains "draft", but its title does not.
   - `"keeps inner spaces in the search text"`: `"support rota"` returns `t-004`, while
     `"supportrota"` and `"support  rota"` return `[]`.
   - `"combines search with status and starredOnly"`: `{ status: "in_progress", starredOnly: true,
     starredIds: new Set(["t-002", "t-006", "t-010"]), search: "re" }` returns `t-002` and `t-006`,
     because `t-010` "Plan accessibility audit" fails the search. Also assert the input is not mutated.
   - `"returns an empty list for an empty input with a search"`: `filterTasks([], { …, search: "rota" })`
     returns `[]`.
3. **UI (`src/App.tsx`):**
   - Add `const [search, setSearch] = useState("");`.
   - Pass `search` in the `filterTasks` query and add it to the `useMemo` dependency array.
   - After the "Starred only" `<input>` inside `<div className="controls">`, add
     `<label htmlFor="search-filter">Search</label>` and
     `<input id="search-filter" type="text" value={search} onChange={(e) => setSearch(e.target.value)} />`.
     There is no `<form>` or submit handler, so filtering happens on every change.
4. **Component tests (`src/App.test.tsx`):** add the tests named in the mapping below. They query by
   role and label (`getByRole("textbox", { name: "Search" })`) and use `userEvent` for typing,
   clearing and Tab navigation.
5. **E2E (`e2e/app.spec.ts`):** add a separate
   `test("searches tasks by title alongside the other filters", …)`. It fills the Search box with
   `"  ROTA "` and expects one list item, "Update support rota", and the text "Showing 1 of 12 tasks". It then
   selects Status "To do" and expects "No tasks match the current filter." and "Showing 0 of 12 tasks". Finally it
   selects "All", clears Search and expects 12 items. The new test does not assert on the page heading
   (see Coordination).
6. Run `npm run lint`, `npm run typecheck`, `npm run test:unit`, `npm run build` and `npm run test:e2e`.

## Risks
| Risk | Mitigation |
|---|---|
| Using `type="search"` would change the accessible role to `searchbox` and break role-based tests and the spec wording | Plan fixes `type="text"`. Tests query `getByRole("textbox", { name: "Search" })` |
| `getByLabelText("Search")` or text queries could collide with other content | Use role + name queries. No other element is named "Search" |
| Adding `search` as a required field would force edits to existing `TaskQuery` literals in tests | Field is optional and a missing value behaves the same as `""`. Existing tests stay untouched |
| Forgetting `search` in the `useMemo` dependencies would leave the list stale | Covered by the AC2/AC6 component tests. `eslint-plugin-react-hooks` exhaustive-deps also flags it |
| Lower-casing differs for some locales (for example Turkish dotted I) | Accepted per spec A2 (standard JS lower-casing, no locale folding). Fixture data is ASCII |
| Merge conflict with SDLC-12 in shared files | Rebase after SDLC-12 merges. New tests avoid heading assertions |

## Rollback implications
Client-only, additive change with no persisted state, storage keys, schemas or migrations. The
search text is never stored. Reverting the feature commit(s) restores the previous behaviour
with no data cleanup. The `TaskQuery.search` field is optional, so reverting cannot break
other callers unless a later ticket starts using it.
