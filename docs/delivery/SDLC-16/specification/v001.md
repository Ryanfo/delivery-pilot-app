# Specification: Search Tasks by Title

> Provenance (ticket, revision, run, inputs) is added by the coordinator on publication.

## Problem and outcome
As the task list grows, users take too long to find a particular task because they cannot
search. Users need a search box with the existing filter controls that narrows the list, as they
type, to tasks whose title contains the typed text.

**Important finding: most of this is already delivered.** Title search was built and merged under
**SDLC-13 "Search by task name"** (commit `03eaed9`, merged in PR #8 and on `main` at
`48583e8`). That work has the same six acceptance criteria as this brief. On the current code:

| Brief criterion | Current behaviour on `main` | Status |
|---|---|---|
| AC1 search input labelled "Search" with the Status and Starred only controls | `<input type="search" id="search-filter" aria-label="Search" placeholder="Search">` sits in the same `.controls` container (`src/App.tsx:71-78`). Its accessible name is "Search", but it has **no visible `<label>`**. SDLC-13 chose that deliberately, and its tests assert that no visible label exists (`src/App.test.tsx:115-128`, `e2e/app.spec.ts:37`). | Partly met: see Q2 |
| AC2 case-insensitive title match, leading/trailing spaces ignored | `matchesSearch` trims and lower-cases (`src/domain/filter.ts:15-19`) | Met |
| AC3 combines with Status and Starred only | `filterTasks` ANDs all three (`src/domain/filter.ts:22-29`) | Met |
| AC4 "Showing X of Y tasks" counts visible tasks | Count uses the filtered list (`src/App.tsx:80-82`) | Met |
| AC5 empty-state message | `TaskList` shows "No tasks match the current filter." (`src/components/TaskList.tsx:10-12`) | Met |
| AC6 clearing shows tasks again | Empty or whitespace-only search matches every task | Met |

The ticket is not linked to SDLC-13 in Jira. Unless this ticket asks for something SDLC-13 did not
deliver, it is a duplicate. The only difference we found is the wording "labelled" in AC1, read
against the project standard that "every control has a visible, associated label"
(`docs/coding-standards.md`). The current input does not meet that standard.

This draft therefore specifies the full behaviour (so it can be reviewed as a whole). It also
records that, if Q1 and Q2 confirm the default, the only change needed is a **visible "Search"
label** on the existing input.

## Scope
- In scope: a title search input in the filter controls above the task list. It filters as the
  user types, ignores case and leading/trailing spaces, combines with the Status and Starred
  only filters, updates the visible-task count, uses the existing empty state, and shows all
  tasks again when cleared.
- In scope (the only change from current `main`, pending Q2): give the search input a visible label
  reading "Search", associated with the input, like the Status and Starred only controls.
- Because AC2–AC6 already pass on `main`, delivery for them means confirming the existing
  tests still pass. No behaviour change is expected.
- No slices proposed: this is a single small outcome.

## Exclusions
- Out of scope: searching task descriptions.
- Out of scope: remembering the search between visits (the search starts empty on every load).
- Out of scope: highlighting the matched text.
- Out of scope: changing the matching rules SDLC-13 established (plain substring, inner spaces
  kept as typed, no regex or fuzzy matching).

## Acceptance criteria
- **AC1**: Given the task list page, when it loads, then a text input with a **visible label
  "Search"** appears in the same filter controls as the Status and Starred only controls. The
  label is programmatically associated with the input (accessible name "Search"). The input is
  empty and can be reached and typed into with the keyboard. *(Visible label pending Q2; on
  current `main` the input has only an `aria-label` and a placeholder.)*
- **AC2**: Given the search input, when the user types text, then the list immediately shows only
  tasks whose title contains that text, ignoring upper/lower case. Spaces at the start or end of
  the typed text are ignored (e.g. "  REVIEW " matches "Review quarterly roadmap").
- **AC3**: Given a search, a Status selection and/or Starred only, when they are applied
  together, then a task is shown only if it matches all of them. Each control keeps its own
  value when the others change.
- **AC4**: Given a search is entered, then the "Showing X of Y tasks" line shows X = the number of
  tasks currently visible after all filters, and Y = the total number of tasks.
- **AC5**: Given a search that matches no visible task, then the existing "No tasks match the
  current filter." message is shown (and the count reads "Showing 0 of Y tasks").
- **AC6**: Given a search has narrowed the list, when the user clears the search box (or leaves
  only spaces in it), then every task allowed by the other active filters is shown again.

## Non-functional requirements
- Accessibility: visible, associated label (project standard). Keyboard operable. The count
  line keeps its existing `aria-live="polite"`, and the empty state keeps `role="status"`.
- Performance: filtering happens on the client with each keystroke, using the existing
  synchronous filtering. No noticeable lag with the fixture data set (12 tasks).
- Security/privacy: no network calls. The search text is not stored.
- Compatibility: browsers already supported by the app. `type="search"` may show a native
  clear control, and using it counts as clearing (AC6).

## Constraints
- Filtering stays in the pure domain layer: extend or reuse `TaskQuery` / `filterTasks` in
  `src/domain/filter.ts`, not ad-hoc filtering in components (`docs/architecture.md`).
- Coding standards and testing policy in `docs/` apply. Existing SDLC-13 tests that assert
  *no* visible label (`src/App.test.tsx:115-128`, `e2e/app.spec.ts:37`) will need to change
  if a visible label is added. That is an intended reversal of SDLC-13's decision, not a
  regression.

## Designs and attachments
None.

## Dependencies
- SDLC-13 "Search by task name" (delivered, merged in PR #8): provides the current search
  behaviour this ticket would build on or duplicate. It is not linked to SDLC-16 in Jira.
- Existing Status and Starred only filters, the count line and the empty-state message.

## Assumptions
- A1: "Title" means the task's `title` field only (descriptions are out of scope).
- A2: Inner spaces in the search are matched as typed. "release notes" matches, but
  "releasenotes" does not. This is current behaviour.
- A3: Regex/special characters are matched literally. This is current behaviour.
- A4: The search starts empty on each page load. This follows from "not remembered between
  visits".

## Open questions
- **Q1**: This brief has the same AC1–AC6 as SDLC-13 "Search by task name", which is already
  delivered and merged (PR #8). Is SDLC-16 meant to change something SDLC-13 delivered, or is it a
  duplicate that should be closed? (If it is a duplicate, no delivery work is needed. The
  proposed default is to treat it as the visible-label change in Q2.)
- **Q2**: In AC1, does "labelled 'Search'" mean a **visible** "Search" label next to the input
  (as for Status and Starred only, and as `docs/coding-standards.md` requires), replacing
  SDLC-13's placeholder-only design? Or is the current `aria-label` and placeholder acceptable?
  (A visible label changes AC1 and reverses SDLC-13's tested decision. Proposed default:
  visible label, keeping the "Search" placeholder.)

## Original brief
**Search Tasks by Title**

With a growing list it takes a while to find a particular task; there is no way to search.
Scope: add a search box to the filter controls above the task list. As you type, the list shows only the tasks whose title contains what you typed.
Acceptance criteria
- AC1: A text input labelled "Search" appears with the existing Status and Starred only controls.
- AC2: Typing filters the list to tasks whose title contains the text, ignoring upper and lower case. Spaces at the start or end of the search are ignored.
- AC3: Search combines with the Status and Starred only filters: a task is shown only if it matches all of them.
- AC4: The "Showing X of Y tasks" line counts only the tasks the search leaves visible.
- AC5: When nothing matches, the existing "No tasks match the current filter." message is shown.
- AC6: Clearing the search box shows the tasks again.
Out of scope: searching task descriptions, remembering the search between visits, highlighting the matched text.
