# Implementation plan: Search by task name

> Provenance is added by the coordinator. Implements the approved specification revision named in the provenance.

## Approach
Extend `TaskQuery` in `src/domain/filter.ts` with a required `search: string` field and apply it
inside `filterTasks` alongside the existing status and starred predicates (logical AND), as
`docs/architecture.md` requires. Matching goes in a small exported pure function,
`matchesSearch(title, search)`. It trims leading and trailing whitespace from the search text,
lowercases both sides with `String.prototype.toLowerCase()` and uses `String.prototype.includes`.
Because it uses `includes`, the text is always a plain substring and never a pattern (spec NFR
Security, A3, A4). An empty or whitespace-only search matches every title (A2).

`App` holds the raw `search` string in React state, so the input shows exactly what the user typed.
It passes that string to `filterTasks` inside the existing `useMemo`, so the list, the
"Showing X of Y tasks" count and the empty state all come from the same `visible` array
(AC4, AC5). Sorting runs after filtering, so result order does not change (A5). The search is not
persisted anywhere (A6).

The control follows spec v002 AC1 (review feedback F1): a single
`<input id="search-filter" type="search" placeholder="Search" aria-label="Search">` with **no**
`<label>` element. The placeholder is the only visible cue; `aria-label` gives the explicit
accessible name "Search", so it is found by `getByRole("searchbox", { name: "Search" })` and by
label queries in Testing Library and Playwright. This is the standards exception the approved
specification records under Constraints; the Status and Starred only controls keep their visible
labels unchanged. The input is the last control in the existing `<div className="controls">` row,
after "Starred only", so the Tab order of the existing controls stays the same (A7).
`type="search"` exposes the `searchbox` role, and its native clear button fires a normal change
event with `""`, which meets AC6 (A8). There is no `autoFocus` (NFR Accessibility) and no debounce
(NFR Performance).

No new dependencies, storage formats or migrations. No ADR is needed: the label exception is a
specification decision already approved, not an architectural one.

## Interfaces and data
- `TaskQuery` (exported interface, `src/domain/filter.ts`) gains `readonly search: string;`.
  The field is required, matching the existing fields, so every caller states its search
  explicitly. The callers today are `App.tsx` and `filter.test.ts`; both are updated here.
- New export: `matchesSearch(title: string, search: string): boolean`. Pure. Returns `true` when
  `search.trim()` is empty, otherwise `title.toLowerCase().includes(search.trim().toLowerCase())`.
- `filterTasks` signature is unchanged. Its predicate gains `&& matchesSearch(task.title, query.search)`.
- `sortTasks`, `Task`, `StatusFilter`, the storage (`starred.ts`) and the `TaskList` props are unchanged.
- No storage format, schema or URL changes.

## Implementation steps
1. **Domain** (`src/domain/filter.ts`):
   - Add `readonly search: string;` to `TaskQuery`.
   - Add `export function matchesSearch(title: string, search: string): boolean` with a one-line
     doc comment ("Case-insensitive title substring match; surrounding whitespace in the search is
     ignored."). Trim the search once, return `true` if empty, otherwise compare the lowercased
     strings with `includes`.
   - In `filterTasks`, AND `matchesSearch(task.title, query.search)` onto the existing predicate.
2. **Domain tests** (`src/domain/filter.test.ts`):
   - Add `search: ""` to each existing `filterTasks` query literal so it typechecks. No other
     change to existing tests.
   - Add `describe("matchesSearch", ...)` covering: empty search; whitespace-only search;
     case-insensitive matching; surrounding spaces trimmed; internal spaces matched literally;
     no match; regular-expression metacharacters treated literally (for example `"("` does not
     throw and matches nothing in the fixtures).
   - Add `filterTasks` search tests using the fixtures (expected IDs below).
3. **UI** (`src/App.tsx`):
   - Add `const [search, setSearch] = useState("");`.
   - Pass `search` into the `filterTasks` query and add it to the `useMemo` dependency array.
   - Inside `<div className="controls">`, after the Starred only checkbox, add
     `<input id="search-filter" type="search" placeholder="Search" aria-label="Search" value={search} onChange={(e) => setSearch(e.target.value)} />`.
     Do **not** add a `<label>` for it (spec v002 AC1, Constraints).
   - Do not change the Status/Starred only labels, the count line, its `aria-live` wrapper or `TaskList`.
   - No styling change: the app ships no CSS, so the placeholder uses the browser default colour
     (see Risks).
4. **Component tests** (`src/App.test.tsx`): add the tests named in the mapping. Query by role and
   name (`getByRole("searchbox", { name: "Search" })`). Type with `userEvent`, clear with `user.clear`.
5. **E2E** (`e2e/app.spec.ts`): add a separate
   `test("searches tasks by title combined with other filters", ...)`. Playwright gives each test a
   fresh context, so starred state from the existing test does not leak into it.
6. Run `npm run lint`, `npm run typecheck`, `npm run test:unit`, `npm run build` and
   `npm run test:e2e`.

jsdom does not render placeholders, so the component tests assert the `placeholder` attribute and
empty value; the e2e test confirms the same in a real browser. The SDLC-13 prefix on the new test
names keeps them distinct from the AC-numbered SDLC-10 tests already in `App.test.tsx`. Existing

none are weakened.

## Coordination
`related_work` is empty for this run. No other in-flight ticket is reported as touching
`src/domain/filter.ts`, `src/App.tsx` or their tests. This change follows SDLC-7 and SDLC-10,
already merged into `main` at `be71a8c`. Making `TaskQuery.search` required is a source change to a
shared type: any later ticket that builds a `TaskQuery` literal must supply `search`, and the
typecheck will flag it. The approved exception to the visible-label rule applies to the Search
input only; later tickets should not treat it as a precedent for other controls.

## Risks
| Risk | Mitigation |
|---|---|
| Making `TaskQuery.search` required breaks other callers | Only `App.tsx` and `filter.test.ts` call it; both are updated. `npm run typecheck` confirms there are no others. |
| Reviewers or verifiers flag the missing visible label against `docs/coding-standards.md` | The approved spec v002 records the exception under Constraints; the plan and tests check AC1 (placeholder + explicit `aria-label`, no `<label>`) instead. |
| Placeholder contrast (WCAG AA) depends on browser defaults, as the app has no CSS | Browser default placeholder colours on the default white input background are close to the AA threshold. Verification should check contrast in the Playwright browser; if it falls short, adding a placeholder colour rule is a follow-up for a human to decide (styling was not otherwise in scope). |
| The spec's "re" example lists four titles, but the fixtures give six | Tests assert the actual six. The spec says "such as", so this matches it. |
| The native clear button on `type="search"` behaves differently across browsers | It fires a normal input/change event with `""` through the same `onChange`. AC6 is tested by clearing the value, so it does not depend on the button. |
| Ambiguous queries: label or text queries for "Search" or "Showing …" could match more than one element | Only one element is named "Search" (by `aria-label`), and no text node reads "Search". Count assertions use `exact: false` on the unique count paragraph, as existing tests do. |
| Lowercasing non-ASCII text (for example Turkish dotted I) | Out of scope by A3; the fixtures are ASCII. |

## Rollback implications
Client-side only. No persisted state, storage keys, schema or migration; the search text is held in
memory only. To roll back, revert the feature commit, which restores `TaskQuery` to its previous
shape. No data cleanup is needed, and users' starred IDs in `localStorage` are not affected.
