# Specification: Search by task name

> Provenance (ticket, revision, run, inputs) is added by the coordinator on publication.

## Problem and outcome
As the task list grows, it takes users longer to find a particular task, and they have no way to
search. This change adds a search box to the filter controls above the task list. As the user
types, the list shows only tasks whose title contains the typed text. Search works together with
the existing Status and Starred only filters.

Current behaviour (at `be71a8c`): the controls row in `src/App.tsx` holds a labelled "Status"
select (All / To do / In progress / Done) and a labelled "Starred only" checkbox. The visible list
comes from `filterTasks` (status and starred) followed by `sortTasks` (priority, then title, then
ID). The `aria-live="polite"` paragraph reads "Showing X of Y tasks · N starred", where X is the
number of visible tasks and Y is the total number of tasks. When no task is visible, `TaskList`
shows "No tasks match the current filter." with `role="status"`. `docs/architecture.md` requires
new query features to extend `TaskQuery` in `src/domain/filter.ts`.

## Scope
- In scope: a text input in the existing controls row, alongside Status and Starred only, that
  shows "Search" as placeholder text inside the field instead of a separate visible label next to
  it, and has the accessible name "Search".
- In scope: filtering by task title only. A task matches if its title contains the search text
  as a substring. Matching ignores case, and spaces at the start or end of the search text are
  ignored.
- In scope: combining search with the Status and Starred only filters (logical AND).
- In scope: the "Showing X of Y tasks" line and the existing empty-state message reflect the
  search.
- In scope: unit, component and end-to-end tests that cover each acceptance criterion, as
  required by `docs/testing-policy.md`.

## Exclusions
- Out of scope: searching task descriptions (or any field other than the title).
- Out of scope: remembering the search between visits (no persistence to storage, URL or
  similar).
- Out of scope: highlighting the matched text in results.
- Out of scope: fuzzy matching, word-by-word matching, accent folding and regular-expression
  or wildcard syntax.
- Out of scope: changes to sorting, starring, the Status and Starred only filters (including
  their existing visible labels), or the "N starred" count.

## Acceptance criteria
- **AC1**: Given the task list page, when it loads, then a text input appears in the same
  controls group as the existing "Status" and "Starred only" controls, and:
  - it shows the placeholder text "Search" inside the field while the field is empty;
  - no separate visible label (such as a `<label>` element with the text "Search") is shown next
    to the field;
  - it has the accessible name "Search" for assistive technology, provided explicitly (for
    example with `aria-label="Search"`) rather than relying on the placeholder alone, so it can be
    found by role and name (for example `getByRole("searchbox" | "textbox", { name: "Search" })`);
  - its value is initially empty, all tasks are shown (subject to the other filters' defaults),
    and the input works from the keyboard (users can Tab to it and type into it).
- **AC2**: Given tasks with various titles, when the user types into Search, then the list
  updates as they type (no submit action) to show only tasks whose title contains the search
  text, ignoring case. Spaces at the start or end of the search text are ignored. Examples using
  the fixture data:
  - "review" and "REVIEW" both show "Review quarterly roadmap" only.
  - "  review  " (with surrounding spaces) gives the same result as "review".
  - "re" shows every task whose title contains "re" in any case, such as "Review quarterly
    roadmap", "Prepare demo environment", "Write release notes" and "Order replacement
    keyboards".
  - Spaces inside the text count as part of the search: "release notes" matches "Write release
    notes", but "releasenotes" matches nothing.
- **AC3**: Given a search text plus a Status selection and/or "Starred only" checked, when the
  list is shown, then a task appears only if it matches the search **and** the selected status
  **and** (if Starred only is checked) is starred. Changing any one filter keeps the others'
  current values.
- **AC4**: Given an active search, when the list updates, then X in "Showing X of Y tasks"
  equals the number of tasks actually shown after search and the other filters. Y stays the total
  number of tasks, and the "· N starred" part keeps counting all starred tasks. The line stays in
  its existing `aria-live="polite"` region so the change is announced.
- **AC5**: Given a search (alone or combined with other filters) that matches no task, when the
  list updates, then the existing message "No tasks match the current filter." is shown (as
  today, with `role="status"`) and the count line reads "Showing 0 of Y tasks".
- **AC6**: Given an active search, when the user clears the Search box (deletes all text, or
  leaves only spaces), then the list again shows every task that matches the other active
  filters, the count line updates to match, and (once the field is empty) the "Search"
  placeholder is shown again.

## Non-functional requirements
- Accessibility: the Search input uses the placeholder "Search" as its only visible cue (F1) and
  has an explicit accessible name "Search" (for example `aria-label`), because a placeholder is
  not a reliable accessible name and disappears once the user types. This is a deliberate,
  ticket-requested exception to `docs/coding-standards.md` ("every control has a visible,
  associated label"); see Constraints. The placeholder text must remain legible against the
  input background (WCAG AA contrast). The input works fully from the keyboard and does not
  steal focus on load. Result changes are announced through the existing `aria-live` count line
  and the `role="status"` empty-state message.
- Performance: filtering is applied on every keystroke and feels instant with the fixture data
  (12 tasks) and with lists of a few hundred tasks. No debounce is required.
- Security and privacy: the search text stays in memory only. It is not persisted, logged or
  sent anywhere (the app has no backend). The search text is treated as plain text, never as a
  pattern or as markup.
- Compatibility: the browsers already supported by the app and its Playwright configuration.

## Constraints
- **Standards exception (F1):** `docs/coding-standards.md` line 7 requires every control to have
  a visible, associated label. At the ticket reviewer's request (F1), the Search input uses a
  placeholder inside the field instead of a visible label next to it. Approving this revision
  approves that exception for the Search input only; the Status and Starred only controls keep
  their visible labels. Review and verification should check the input against AC1 (placeholder
  plus explicit accessible name), not against the visible-label rule.
- Follow `docs/architecture.md`: extend `TaskQuery` in `src/domain/filter.ts` (pure, no React,
  no I/O) instead of filtering ad hoc in components. State lives in `App`.
- TypeScript strict rules from `docs/coding-standards.md` apply. No new runtime dependencies
  (`docs/guardrails.md`).
- Synthetic fixture data only.
- Each acceptance criterion maps to at least one named test. Domain unit tests cover empty input,
  case handling, surrounding spaces and combined filters (`docs/testing-policy.md`). The AC1
  tests check the placeholder, the accessible name, and that no visible "Search" label element is
  rendered.

## Assumptions
- **A1**: "Y" in "Showing X of Y tasks" stays the total number of tasks, and "N starred" stays
  the total number of starred tasks. Search changes only X, consistent with how the existing
  filters behave.
- **A2**: A search box that contains only spaces counts as empty and shows all tasks (subject to
  other filters). This follows from "spaces at the start or end are ignored".
- **A3**: Case-insensitive matching uses standard JavaScript lowercasing (or an equivalent), with
  no accent or diacritic folding. All fixture titles are plain ASCII.
- **A4**: Only leading and trailing whitespace is trimmed. Internal spaces are matched literally
  and are not collapsed.
- **A5**: Search results keep the existing sort order (priority, then title, then ID).
- **A6**: The search resets to empty on page reload, which follows from "remembering the search
  between visits" being out of scope.
- **A7**: Placement and order within the controls row are not specified. Putting Search alongside
  the existing controls (for example first or last in the row) meets AC1. Exact placement and
  styling are for the plan stage.
- **A8**: Whether the input uses `type="search"` (with a native clear button) or `type="text"` is
  an implementation choice. Either way, clearing the text must meet AC6.
- **A9**: F1 ("the label as a placeholder within the field, rather than a label next to the
  field") means the visible text "Search" moves into the field as a placeholder and no visible
  label is rendered, while the input keeps the accessible name "Search" so screen-reader users
  still get a label.

## Open questions

## Original brief
**Summary:** Search by task name

**Description:**

With a growing list it takes a while to find a particular task; there is no way to search.
Scope: add a search box to the filter controls above the task list. As you type, the list shows only the tasks whose title contains what you typed.
Acceptance criteria
- AC1: A text input labelled "Search" appears with the existing Status and Starred only controls.
- AC2: Typing filters the list to tasks whose title contains the text, ignoring upper and lower case. Spaces at the start or end of the search are ignored.
- AC3: Search combines with the Status and Starred only filters: a task is shown only if it matches all of them.
- AC4: The "Showing X of Y tasks" line counts only the tasks the search leaves visible.
- AC5: When nothing matches, the existing "No tasks match the current filter." message is shown.
- AC6: Clearing the search box shows the tasks again.
Out of scope: searching task descriptions, remembering the search between visits, highlighting the matched text.
