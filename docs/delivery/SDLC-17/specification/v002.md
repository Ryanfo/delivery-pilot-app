# Specification: Styling

> Provenance (ticket, revision, run, inputs) is added by the coordinator on publication.

## Problem and outcome
The task list page currently has no styling at all: there is no stylesheet anywhere in the app,
so the page renders with browser defaults (Times on white, unstyled form controls, bulleted list,
default heading sizes). The `controls` and `task-list` class names in `src/App.tsx` and
`src/components/TaskList.tsx` have no styles behind them.

The ticket asks for the page to be styled in an "editorial" way and leaves the interpretation to
us. The outcome: the page reads like a well-typeset publication page. It has a masthead, a
deliberate type hierarchy, a calm "paper and ink" palette, a comfortable reading measure and
clear rules between tasks. All existing behaviour, text and accessibility stay the same, except
that the "Welcome" / "HELLO WORLD" section is removed from the page (A4).

**Interpretation of "editorial" used by this specification** (see Assumptions A1):
- **Typography first**: a serif display face for the masthead and task titles, a readable body
  face, and small uppercase, letter-spaced "kicker" text for metadata and labels.
- **Restrained palette**: off-white paper background, near-black ink text, one accent colour
  for emphasis (starred state, focus, links/controls), and muted grey for secondary text.
- **Single column with a reading measure**: content centred in a column of about 40 to 48rem
  (roughly 65 to 75 characters of body text) with generous vertical rhythm.
- **Rules instead of boxes**: thin horizontal rules separate the masthead, the controls and
  each task, instead of cards, shadows or rounded panels.

## Scope
- In scope:
  - Adding a global stylesheet, loaded by the app, that styles the whole page: the page
    background and body text, the `h1` masthead, the controls bar (Status select, Starred only
    checkbox, Search field), the results count line, the task list and each task (title,
    description, metadata line, star button) and the empty state message.
  - Removing the `<section aria-label="Welcome">HELLO WORLD</section>` block (delivered by
    SDLC-7) from `src/App.tsx`, and updating the two SDLC-7 assertions that pinned it
    (`src/App.test.tsx`, `e2e/app.spec.ts`) to assert that the region is absent.
  - Light markup changes needed only to attach styles (for example class names or wrapper
    elements), as long as the visible text, roles, accessible names and DOM order that users and
    tests rely on stay the same.
  - Responsive layout from 320px wide upwards.
  - Visible keyboard focus styling for every interactive control.

## Exclusions
- Out of scope:
  - Any change to behaviour: filtering, sorting, search, starring, persistence or counts.
  - Any change to visible copy, including the masthead text "Task list", control labels, the
    search placeholder, the results line and the empty-state message. (The removal of the
    "HELLO WORLD" welcome section is the one exception; see Scope and A4.)
  - Adding a visible label for the Search field. It deliberately has none (SDLC-13; the e2e test
    asserts there is no `label[for="search-filter"]`).
  - Web fonts loaded from an external service (for example Google Fonts) and new runtime
    dependencies (CSS frameworks, CSS-in-JS libraries, icon packs).
  - A dark theme or theme toggle, print stylesheets, animations beyond simple hover/focus
    transitions, images or illustrations.
  - New UI features (for example a date line, bylines, task categories or "lead story" layouts
    that need data the app does not have).

## Acceptance criteria
- **AC1**: Given the app is loaded, when the page renders, then a stylesheet bundled with the
  app is applied: the page background is an off-white "paper" colour (not pure `#ffffff`), and
  body text is a near-black "ink" colour (not pure `#000000`).
- **AC2**: Given the page renders, then the "Task list" `h1` is styled as a masthead: set in a
  serif font stack, visibly larger than every other text on the page, centred or left-aligned
  across the content column, and separated from the content below by a horizontal rule
  (a border or `hr`-style divider).
- **AC3**: Given the page renders, then task titles (`h2` in each task) use the same serif
  family as the masthead. Description text uses a readable body font stack at a base size of at
  least 16px with a line-height between 1.4 and 1.7.
- **AC4**: Given the page renders, then each task's metadata line (status, priority and due date
  where present) and the control labels ("Status", "Starred only") are styled as secondary
  "kicker" text: smaller than body text, uppercase via CSS (`text-transform`, without changing
  the DOM text), letter-spaced and in the muted secondary colour.
- **AC5**: Given a viewport 1280px wide, then the page content (masthead, controls, results line
  and task list) sits in a single centred column no wider than 48rem with horizontal margins on
  both sides.
- **AC6**: Given the task list has tasks, then the list has no bullet markers, and consecutive
  tasks are separated by a thin horizontal rule with consistent vertical spacing between them.
  Tasks are not drawn as cards: no box shadows and no rounded, filled backgrounds.
- **AC7**: Given the controls bar, then the Status select, the Starred only checkbox and its
  label, and the Search field are laid out on one row when the viewport is at least 768px wide,
  and wrap onto multiple rows without horizontal page scrolling when the viewport is narrower.
  Form controls use the page's fonts and palette rather than browser-default fonts.
- **AC8**: Given a task is starred, then its star button is visually distinct from an
  unstarred one through the accent colour and fill, in addition to the existing "★ Starred" /
  "☆ Star" text, so the state is never conveyed by colour alone.
- **AC9**: Given any interactive control (select, checkbox, search field, star button) receives
  keyboard focus, then a clearly visible focus indicator is shown, at least a 2px outline or
  ring in the accent colour, with a contrast ratio of at least 3:1 against the paper background.
  Focus outlines are never removed without a replacement.
- **AC10**: Given the styled page, then all text meets WCAG 2.1 AA contrast against its
  background: at least 4.5:1 for body, metadata, label, placeholder and results text, and at
  least 3:1 for large text (masthead and task titles).
- **AC11**: Given a viewport 320px wide, then the page has no horizontal scrolling, and all text
  and controls stay readable and usable.
- **AC12**: Given no tasks match the filter, then the "No tasks match the current filter."
  message is styled consistently with the page (body font, muted or italic editorial
  treatment) and keeps `role="status"`.
- **AC13**: Given the styling change, then all existing visible text, roles, accessible names,
  `aria-*` attributes, `data-testid` values and element order are unchanged, except that the
  "Welcome" region (`<section aria-label="Welcome">` with the text "HELLO WORLD") is removed
  from the page. The existing unit, component and end-to-end tests pass without being modified
  to accommodate the styling, except the SDLC-7 welcome assertions in `src/App.test.tsx` and
  `e2e/app.spec.ts`, which now assert that the "Welcome" region and the "HELLO WORLD" text are
  absent.

## Non-functional requirements
- **Accessibility**: WCAG 2.1 AA contrast (AC10), visible focus (AC9), state not by colour
  alone (AC8). Text must still scale with browser zoom up to 200% without loss of content: use
  relative units (`rem`/`em`) for font sizes. Respect `prefers-reduced-motion` by disabling any
  transitions.
- **Performance**: styles are bundled by Vite with the app; no extra network requests at
  runtime. The stylesheet should stay small (a single file of a few KB is expected).
- **Compatibility**: current evergreen browsers (the Playwright browser used by `npm run
  test:e2e` at minimum). Fonts come from system font stacks with generic `serif` / `sans-serif`
  fallbacks, so the page degrades gracefully when a named font is not installed.
- **Security/privacy**: no external resources (fonts, images, CDNs) are loaded.

## Constraints
- Client-only React + TypeScript + Vite app (`docs/architecture.md`). Styling should use plain
  CSS imported through Vite (which supports it without new dependencies). The plan stage
  decides the exact mechanism.
- `docs/guardrails.md`: no new runtime dependencies without an explicit plan decision, and no
  external services. External web fonts are therefore excluded (see Exclusions).
- `docs/coding-standards.md`: components stay thin, and accessibility rules (labels, keyboard
  operability, live regions) must not regress.
- `docs/testing-policy.md`: each acceptance criterion maps to at least one named test, and
  existing tests must not be weakened. Purely visual criteria (AC1 to AC12) are expected to be
  checked with computed-style assertions in Playwright (a real browser; jsdom does not apply
  stylesheets) and/or by human review of screenshots. The plan stage decides which.
- Must not touch `.github/`, `CLAUDE.md`, `.claude/` or `docs/delivery/`.

## Designs and attachments
None. No attachments or Figma designs were provided. The visual direction comes from this
specification's interpretation of "editorial" (Problem and outcome; Assumption A1).

## Dependencies
- Existing UI in `src/App.tsx` (masthead, welcome section to be removed, controls, results
  line) and `src/components/TaskList.tsx` (task list, task items, star button, empty state).
- Existing tests that pin text, roles and attributes: `e2e/app.spec.ts`, `src/App.test.tsx`.
- SDLC-7 (delivered): its "HELLO WORLD" welcome block is removed by this ticket, which retires
  that ticket's delivered behaviour. No in-flight related work is listed for this ticket.

## Assumptions
- **A1**: "Editorial" means a typography-led, newspaper/magazine-like look as described in
  "Interpretation of 'editorial'" above: serif display type, paper-and-ink palette with one
  accent colour, a single reading column and horizontal rules. The brief delegates this choice
  ("however you interpret that"); the spec reviewer can redirect it.
- **A2**: Exact colour values, font stacks, spacing scale and the accent hue are left to the
  plan/implementation, within the constraints of the acceptance criteria (contrast, no external
  fonts).
- **A3**: "The page" means the single page the app has: the task list page.
- **A4**: The "Welcome" / "HELLO WORLD" section (delivered by SDLC-7) is removed from the page,
  at the developer's request. The masthead is followed directly by the controls bar.
- **A5**: Light mode only. The page does not need to adapt to `prefers-color-scheme: dark`.
- **A6**: The Search field keeps no visible label (SDLC-13 behaviour), relying on its
  placeholder and `aria-label`. The placeholder text must still meet AC10 contrast.

## Open questions
None blocking. Reviewers may challenge Assumption A1 (the interpretation of "editorial") or A5
(light mode only) in feedback if a different direction is wanted.
