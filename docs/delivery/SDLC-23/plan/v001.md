# Implementation plan: Let users change a task's priority with a dropdown

> Provenance is added by the coordinator. Implements the approved specification revision named in the provenance.

## Approach
Follow the per-task Status dropdown delivered in SDLC-18 exactly, as the specification asks:

- **Domain** (`src/domain/task.ts`): add `TASK_PRIORITIES`, `PRIORITY_LABELS`, `isTaskPriority` and a
  pure `withPriorities(tasks, overrides)` that mirrors `withStatuses`.
- **Storage** (`src/storage/priorities.ts`): add `loadPriorities` / `savePriorities` under the key
  `task-list:priority:v1`. They mirror `src/storage/statuses.ts`, so corrupt, invalid or unavailable
  storage falls back the same way.
- **State** (`src/App.tsx`): keep a `priorities` map in React state, loaded once from the store. The
  derived task list becomes `withPriorities(withStatuses(tasks, statuses), priorities)`. Because
  `filterTasks` and `sortTasks` already read `task.priority` and `task.status` from that list,
  filtering, sorting and the results line pick up changed priorities with no change to
  `src/domain/filter.ts` (AC6, AC7).
- **UI** (`src/components/TaskList.tsx`): add a labelled native `<select>` after the Status dropdown
  in each task's `.task-actions`. It has a visible "Priority" label, a visually hidden
  "for <task title>" suffix and the options Low, Medium and High. Placing it last keeps the existing
  tab order (star → Status) that current tests rely on (assumption A4 left the position to the plan).
  The `Priority: <value>` meta text is unchanged and shows the current (possibly overridden) lowercase
  value (A3).

No new dependencies, no changes to `filter.ts`, `starred.ts` or `statuses.ts`, and no ADR is needed:
this reuses an established pattern.

## Interfaces and data
- `src/domain/task.ts` (new exports):
  - `export const PRIORITY_LABELS: Readonly<Record<TaskPriority, string>> = { low: "Low", medium: "Medium", high: "High" }`
  - `export const TASK_PRIORITIES: readonly TaskPriority[] = ["low", "medium", "high"]` (option order for AC1)
  - `export function isTaskPriority(value: unknown): value is TaskPriority`
  - `export function withPriorities(tasks: readonly Task[], overrides: ReadonlyMap<string, TaskPriority>): Task[]`.
    It applies overrides by ID, ignores unknown IDs, never mutates the input, keeps the input order and
    returns the same object when nothing changes. `Task` and `TaskPriority` are unchanged.
- `src/storage/priorities.ts` (new module):
  - `export const PRIORITY_KEY = "task-list:priority:v1"`
  - `export function loadPriorities(store: KeyValueStore | undefined): Map<string, TaskPriority>`. It
    returns an empty map for a missing key, invalid JSON, a non-object, or any thrown error, and drops
    entries whose value is not low/medium/high.
  - `export function savePriorities(store: KeyValueStore | undefined, priorities: ReadonlyMap<string, TaskPriority>): boolean`.
    It writes a JSON object with sorted keys and returns `false` (no throw) when storage is
    unavailable or throws.
  - It reuses `KeyValueStore` from `./starred`.
- **Storage format:** `localStorage["task-list:priority:v1"] = {"<taskId>": "low"|"medium"|"high", ...}`.
  This key is new; the starred and status keys are untouched. Per A5, an entry stays stored even if
  the user later picks the fixture value again.
- `TaskList` props: add `readonly onChangePriority: (id: string, priority: TaskPriority) => void`.
- DOM: the select gets `id="task-priority-<taskId>"`. Its label (`htmlFor` that ID) has
  `className="task-priority-label"` and the text `Priority <span class="visually-hidden">for <title></span>`,
  so the accessible name is "Priority for <task title>".

## Implementation steps
1. **Domain.** In `src/domain/task.ts`, add `PRIORITY_LABELS`, `TASK_PRIORITIES`, `isTaskPriority` and
   `withPriorities`, modelled line for line on the status equivalents. Add unit tests to
   `src/domain/task.test.ts` (names in the mapping below).
2. **Sorting check.** In `src/domain/filter.test.ts`, add a `sortTasks` test that applies
   `withPriorities(TASKS, new Map([["t-003", "high"]]))` and asserts `t-003` ("Book team
   retrospective") sorts first: high group, then title. Also check the remaining order is unchanged.
   No production change to `filter.ts`.
3. **Storage.** Create `src/storage/priorities.ts`, mirroring `statuses.ts` (an `isRecord` guard,
   `isTaskPriority` validation, try/catch at the boundary). Create `src/storage/priorities.test.ts`,
   mirroring `statuses.test.ts`.
4. **App state.** In `src/App.tsx`:
   - add `const [priorities, setPriorities] = useState<Map<string, TaskPriority>>(() => loadPriorities(store));`
   - change `current` to `useMemo(() => withPriorities(withStatuses(tasks, statuses), priorities), [tasks, statuses, priorities])`
   - add `changePriority(id, next)`, which copies the map, sets the entry, calls `savePriorities`
     inside the updater (as `changeStatus` does) and returns it
   - pass `onChangePriority={changePriority}` to `TaskList`

   The results line already uses `visible.length`, `tasks.length` and `starred.size`, so it needs
   no change.
5. **UI.** In `src/components/TaskList.tsx`, after the Status `<select>`, add the Priority label and
   select. Its value is `task.priority`; its `onChange` calls
   `if (isTaskPriority(e.target.value)) onChangePriority(task.id, e.target.value)`; its options come
   from `TASK_PRIORITIES.map((p) => <option key={p} value={p}>{PRIORITY_LABELS[p]}</option>)`. Leave
   the `Priority: {task.priority}` meta span as it is.
6. **Styles.** In `src/styles.css`, change the `.task-status-label` selector to
   `.task-status-label, .task-priority-label` so the kicker style, muted colour and left margin
   match. The existing `.task-actions select` and `select:focus-visible` rules already cover the new
   select (body font, 0.875rem, 2px accent focus ring). Update the comment to "star button, then the
   task's status and priority controls".
7. **Adjust two existing tests minimally** (unavoidable once each task has a second combobox; see F1).
   The assertions stay as strong as before, and only the queries are scoped to the Status control:
   - `src/App.test.tsx`, test "gives every task a status control named for the task, … (SDLC-18 AC1)":
     change `within(taskItem(task.title)).getByRole("combobox")` to
     `within(taskItem(task.title)).getByRole("combobox", { name: \`Status for ${task.title}\` })`.
     It still proves the named Status control belongs to that task.
   - `e2e/styling.spec.ts`, test "AC11 has no horizontal scrolling and keeps controls usable at
     320px": select the task Status controls with `getByRole("combobox", { name: /^Status for / })`,
     keeping `toHaveLength(12)`. Add the 12 Priority controls
     (`getByRole("combobox", { name: /^Priority for / })`, also `toHaveLength(12)`) to the
     bounds-checking loop, so the test checks more than before.
8. **Component tests.** Add `describe("App task priority (SDLC-23)")` to `src/App.test.tsx`, reusing
   the `memory()` store and the SDLC-18 helper pattern (`items`, `taskItem`, `priorityControl(title)`,
   `displayedPriority(title)` = the task's `Priority: …` span text, `results`).
9. **E2E.** Add the journey test to `e2e/app.spec.ts` and the styling test to `e2e/styling.spec.ts`
   (names below).
10. Run `npm run lint`, `npm run typecheck`, `npm run test:unit`, `npm run build` and `npm run test:e2e`
    (with `E2E_PORT` set by the coordinator).

## Coordination
`related_work` is empty for this run, so no in-flight ticket's footprint overlaps. This builds on
SDLC-18 (per-task Status dropdown, already merged) and follows its patterns. It changes the composition

## Risks
| Risk | Mitigation |
|---|---|
| **F1, spec conflict:** AC8 says existing tests "keep passing unchanged", but a second per-task `<select>` necessarily adds a second `combobox` to each task. Two existing tests break on query ambiguity alone: `src/App.test.tsx` SDLC-18 AC1 (`within(item).getByRole("combobox")` throws on multiple matches) and `e2e/styling.spec.ts` AC11 (expects 12 list comboboxes; there will be 24). No accessible native dropdown avoids this. | Step 7: scope those two queries to the Status control by accessible name, keep every assertion, and extend AC11 to cover the Priority controls. No test is skipped, deleted or weakened. The plan reviewer should confirm this is acceptable under AC8. If not, the specification needs revising. |
| Re-sorting moves the changed task (AC6). Browsers can drop focus when React reorders a focused element. | Accepted by spec A6 (no extra focus management, same as Status). Tests don't assert focus after a change that moves the task; the keyboard component test uses a single-task list. |
| Tab order changes for keyboard users: the Priority control now follows Status in every task. | Placed last so existing star → Status order (and the SDLC-18 AC5 / styling AC9 tests) is preserved. |
| jsdom cannot emulate arrow keys on a native `<select>`. | Same split as SDLC-18: component test uses Tab plus `selectOptions`; the e2e test uses real keystrokes. |
| At 320px, more controls in `.task-actions` could overflow. | `.task-actions` already wraps (`flex-wrap`) and `select` has `max-width: 100%`; extended AC11 asserts every Priority control stays within 320px. |
| Saving inside the state updater runs twice under React StrictMode. | Idempotent write of the same map; same as the existing `changeStatus` / `toggleStar`. |

## Rollback implications
Revert the commit(s). There is no migration or schema change and no server state. Browsers that used
the feature keep a `task-list:priority:v1` entry in `localStorage`. The reverted code never reads
that key, so it is harmless and the fixture priorities show again. The starred and status keys are
never written by this change, so they are unaffected either way.
