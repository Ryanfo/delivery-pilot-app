# Specification: Let users change a task's priority with a dropdown

> Provenance (ticket, revision, run, inputs) is added by the coordinator on publication.

## Problem and outcome
Each task has a priority (low, medium or high) that users can read in the task list ("Priority: high") but cannot change. Users who re-prioritise their work have no way to do it in the app.

Outcome: every task in the list has a labelled "Priority" dropdown. Choosing a value changes that task's priority straight away, the change is stored in the browser like starred tasks and task statuses, and it is still there after a page reload. Filters, sorting and the results line use the changed priorities.

Current behaviour (from the code at `31b7f95`):
- Priority is fixed fixture data (`src/data/tasks.ts`) and shown read-only in each task's meta line as `Priority: <value>` with the lowercase value, e.g. `Priority: high` (`src/components/TaskList.tsx`).
- The list is sorted by priority (high, medium, low), then title, then ID (`sortTasks` in `src/domain/filter.ts`).
- Each task already has a per-task Status dropdown (visible label "Status", accessible name "Status for <task title>"). Its value is stored in the browser under its own key and applied over the fixture data (`src/storage/statuses.ts`, `withStatuses` in `src/domain/task.ts`). Starred tasks are stored the same way (`src/storage/starred.ts`). Both use `localStorage` and fall back safely when storage is corrupt or unavailable.

## Scope
- In scope: a Priority dropdown on every task in the task list, with options Low, Medium and High, showing the task's current priority.
- In scope: changing a task's priority updates its "Priority: ..." text, its place in the sort order, and anything else derived from the task list, straight away.
- In scope: storing changed priorities in the browser (same mechanism and resilience as starred tasks and task statuses) and applying them on load.
- In scope: unit, component and end-to-end tests for the above.
- No slices proposed: this is one small, coherent change.

## Exclusions
- Out of scope: filtering by priority, or any new filter or sort option.
- Out of scope: changing the priority values themselves (still low, medium, high) or the sort rule (still highest priority first).
- Out of scope: a "reset to original priority" action, bulk changes, or undo.
- Out of scope: syncing priorities to a server or across browsers/devices (the app has no backend).
- Out of scope: any change to the Status dropdown, starring, search, the global filters or the results line beyond them using the changed priorities.

## Acceptance criteria
- **AC1**: Given the task list is shown, then each task has a dropdown with a visible, associated label "Priority" and the accessible name "Priority for <task title>", with exactly three options in this order: Low, Medium, High; and its selected value is the task's current priority (the stored change if there is one, otherwise the fixture priority).
- **AC2**: Given a task, when the user chooses a different value in its Priority dropdown (by mouse or keyboard), then that task's "Priority: ..." text shows the new priority immediately, without a reload, and the dropdown shows the chosen value.
- **AC3**: Given several tasks, when the user changes one task's priority, then no other task's priority dropdown value or "Priority: ..." text changes.
- **AC4**: Given the user has changed one or more tasks' priorities, when the page is reloaded, then those tasks show the changed priorities (dropdown value and "Priority: ..." text) and all other tasks show their original priorities. Priorities are stored in the browser's `localStorage`, in the same way as starred tasks, under their own key.
- **AC5**: Given stored priority data that is missing, unreadable (not valid JSON or the wrong shape), refers to unknown task IDs, or contains values other than low/medium/high, or storage that is unavailable or throws, then the app still renders, ignores the invalid entries, uses the original priority for affected tasks, and changing a priority still works for the current page view.
- **AC6**: Given a task's priority has been changed, then the list is sorted using the changed priority (highest first, then title, then ID), so the task moves to its new position immediately and keeps it after a reload.
- **AC7**: Given a task's priority has been changed, then the Status filter, the Starred only filter and search still return the same tasks as before the change, and the "Showing X of Y tasks · N starred" line stays correct.
- **AC8**: Unit tests cover applying priority changes to tasks (including no changes, unknown IDs and not mutating the input) and loading/saving stored priorities (including missing, corrupt and unavailable storage); component tests cover the Priority dropdown through its role and label, including keyboard use; and an end-to-end test changes a task's priority, checks the text and sort position, reloads and checks the change is kept. Existing tests keep passing unchanged.

## Non-functional requirements
- Accessibility: the dropdown is a native, keyboard-operable control with a visible, associated label, matching the Status dropdown's pattern (visible "Priority" plus visually hidden "for <task title>"). It meets the existing styling checks for per-task controls (contrast, visible focus indicator, body font).
- Performance: no noticeable delay; with 12 fixture tasks, the update is instantaneous.
- Privacy/security: only task IDs and priority values are stored, locally in the browser. No network calls.
- Compatibility: browsers already supported by the app (the Playwright configuration).

## Constraints
- Client-only React + TypeScript app; follow `docs/architecture.md` (pure domain functions in `src/domain/`, persistence in `src/storage/`, state in `App`) and `docs/coding-standards.md` (strict TypeScript, no `any`, stable keys, errors handled at the storage boundary).
- No new runtime dependencies (`docs/guardrails.md`).
- Do not change `.github/`, `CLAUDE.md`, `.claude/` or `docs/delivery/`.
- Each acceptance criterion maps to at least one named test (`docs/testing-policy.md`). Do not weaken, skip or delete existing tests.

## Designs and attachments
None.

## Dependencies
- Existing per-task Status dropdown and status storage (delivered previously, SDLC-18), which this follows as the precedent for layout, labelling and storage.
- Existing starred-task storage (`KeyValueStore`, `browserStore`), named in the brief as the model for storing priorities.
- Existing `sortTasks` priority ordering and `filterTasks`.

## Assumptions
- **A1**: "The change lasts for the current session and is kept after a page reload" plus "stored in the browser, in the same way as starred tasks" means `localStorage` with a versioned key of its own (like `task-list:starred:v1` and `task-list:status:v1`). Changes therefore also survive closing the browser, as starred tasks do. `sessionStorage` is not used.
- **A2**: The accessible name follows the Status dropdown convention: "Priority for <task title>". The visible label is "Priority".
- **A3**: The "Priority: ..." text keeps its current format (lowercase value, e.g. `Priority: high`). Only the value changes. The dropdown options use the capitalised labels Low, Medium and High from the brief.
- **A4**: The Priority dropdown sits in each task's actions area with the Star button and the Status dropdown, and is styled like the Status dropdown. Its exact position within that area is left to the plan.
- **A5**: Choosing the value that is already selected changes nothing. Once a task's priority has been changed, its entry stays stored, even if the user picks the original value again.
- **A6**: Because the list re-sorts immediately (AC6), the changed task can move. No extra focus management is required beyond what the existing Status dropdown does when a change moves or hides its task.
