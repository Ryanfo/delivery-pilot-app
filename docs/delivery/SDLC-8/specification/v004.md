# Specification: Style the task list page with a clean, accessible look

> Provenance (ticket, revision, run, inputs) is added by the coordinator on publication.

## Problem and outcome
The task list page (`src/App.tsx`, `src/components/TaskList.tsx`) currently renders with no
custom styling at all — browser defaults only, no stylesheet, no class-based visual structure.
This makes tasks hard to scan (no visual separation between cards, no distinct status
indicator) and makes the app look unfinished. The outcome is a single, small, dependency-free
stylesheet that gives the existing page a clean, accessible visual design — centred layout,
card-based task list, coloured status badges, visible focus states, and cards that reveal
themselves as the user scrolls to them — without changing any task data, filtering, sorting,
starring behaviour, or text content.

## Scope
- Add one global stylesheet, e.g. `src/styles.css`, imported once from `src/main.tsx`.
- Define colours, spacing and font sizes once as CSS custom properties (design tokens) in
  that stylesheet.
- Add class names to the existing markup in `src/App.tsx` and `src/components/TaskList.tsx`
  as needed to hook up styling (no markup restructuring beyond adding attributes/classes,
  except as needed to satisfy AC2/AC3/AC8 below).
- Page: a centred content column (max width 720px), comfortable padding, system font stack.
- Header: the "Task list" heading styled and visually grouped at the top of the page (the
  brief's reference to a "HELLO WORLD" welcome block does not apply — see Exclusions).
- Status filter (`#status-filter` and its label in `src/App.tsx`): label and select shown on
  one line with clear spacing.
- Task list (`src/components/TaskList.tsx`): each task (`<li>`) styled as a card (border or
  subtle shadow, rounded corners, spacing between cards); title, description and the
  status/priority/due line visually distinct from one another.
- Task status shown as a coloured badge, with a different colour per status (`To do`,
  `In progress`, `Done`), status text remaining visible (colour is not the only signal).
- Star button (`<button>` in `TaskList.tsx`): clear default, hover and starred/pressed visual
  states, built from the existing `aria-pressed` attribute and label text.
- A visible keyboard focus outline on every interactive element (the status `<select>` and
  every star `<button>`).
- Task cards animate into view (a lazy-reveal effect, e.g. fade and/or slide) as the user
  scrolls each card into the viewport, per comment 104680 (`SDLC-8-REFINE-R2`): this
  requirement is explicitly confirmed to supersede the brief's own "no animations" exclusion
  for this one interaction (see Open questions, now resolved, and Exclusions).

## Exclusions
- Dark mode.
- Animations and transitions, **except** the scroll-triggered card reveal added in this
  revision (see Scope and AC8). No other new animated/transitioned effects are in scope —
  the default/hover/pressed star states and badge colours remain instant, non-animated state
  changes.
- New React components (styling applies to the existing `App` and `TaskList` components).
- True lazy loading of data (deferred fetch, pagination, code-splitting) or virtualization
  that removes cards from the DOM/accessibility tree before they are scrolled to: the task
  list is a fixed, synthetic, 12-item array with no backend, so there is no loading cost to
  defer. "Lazy load" in this revision means the scroll-triggered visual reveal in AC8, not a
  change to what is rendered or accessible — see Assumptions.
- A "HELLO WORLD" welcome block: it does not exist in the current codebase and ships in a
  separate, not-yet-merged pull request, so it is out of scope for this ticket.
- CSS frameworks or utility libraries (e.g. Tailwind, Bootstrap) or any new runtime/dev
  dependency.
- Any change to task data (`src/data/tasks.ts`), filtering or sorting logic
  (`src/domain/filter.ts`), starring behaviour or persistence (`src/storage/starred.ts`), or
  existing visible text content (headings, labels, button text, status copy).

## Acceptance criteria
- **AC1**: The page uses a single stylesheet with CSS custom properties for colours, spacing
  and font sizes; no inline `style` attributes are added to any component.
- **AC2**: Each task is shown as a visually separate card (border or shadow, rounded corners,
  spacing between cards), with the title, description and status/priority/due line visually
  distinguishable from each other.
- **AC3**: Task status is shown as a badge whose colour differs for To do, In progress and
  Done, and the status text itself stays visible so colour is not the only signal conveying
  status.
- **AC4**: All text, including badge text, meets WCAG 2.2 AA contrast (at least 4.5:1 for
  normal text) against its background.
- **AC5**: The status filter `<select>` and every star `<button>` show a visible focus
  indicator when reached by keyboard (e.g. Tab).
- **AC6**: At a 375px-wide viewport the page has no horizontal scrolling and all content
  (heading, filter, cards, badges, buttons) stays readable.
- **AC7**: Existing behaviour (task data, filtering, sorting, starring and its persistence,
  all visible text content) is unchanged, and all configured checks pass: lint, typecheck,
  unit, build, e2e.
- **AC8**: Each task card visually reveals itself (e.g. fades and/or slides in) as it is
  scrolled into the viewport; all cards remain present in the DOM and reachable by assistive
  technology and keyboard regardless of scroll position (the reveal is a visual effect only,
  not deferred rendering); for users with a `prefers-reduced-motion: reduce` preference, the
  reveal motion is removed or reduced to an instant appearance.

## Non-functional requirements
- **Accessibility**: WCAG 2.2 AA text contrast (AC4); visible keyboard focus indicators on
  every interactive element (AC5); status conveyed by text as well as colour (AC3); the
  scroll reveal in AC8 respects `prefers-reduced-motion` and never removes content from the
  DOM or accessibility tree; no regression to existing accessibility properties
  (`aria-live`, `aria-pressed`, `aria-label`, associated `<label for>` on the status filter —
  see `docs/coding-standards.md`).
- **Responsive layout**: no horizontal scroll and all content remains readable down to a
  375px viewport width (AC6); centred column capped at 720px on wider viewports.
- **No new dependencies**: achieved with plain CSS and native browser APIs only (e.g.
  `IntersectionObserver` for the scroll reveal), per `docs/guardrails.md` ("No new runtime
  dependencies without an explicit decision in the plan").
- **Compatibility**: uses an OS/browser system font stack; no web font loading.
- **Maintainability**: a single stylesheet with CSS custom properties as the one place
  colours, spacing and font sizes are defined, per AC1.

## Constraints
- Plain CSS only (no CSS-in-JS, no CSS framework, no new dependency) per
  `docs/guardrails.md`; the scroll reveal (AC8) must use a native browser API (e.g.
  `IntersectionObserver`) rather than a new animation/scroll library.
- One global stylesheet imported from `src/main.tsx`; no per-component stylesheets.
- No inline styles (AC1).
- No change to `src/domain/`, `src/data/`, `src/storage/` modules or their tests — this is a
  presentation-only change confined to `src/App.tsx`, `src/components/TaskList.tsx` and the
  new stylesheet.
- Must not touch `.github/`, `CLAUDE.md`, `.claude/` or `docs/delivery/` (guardrail).
- TypeScript strict mode and existing lint rules continue to apply; no suppressions
  (`docs/coding-standards.md`).
- Per `docs/testing-policy.md`, each acceptance criterion needs at least one named test
  (component tests via Testing Library for AC1–AC5 and AC7 behavioural parts; a Playwright
  viewport check for AC6; existing unit/e2e tests must continue to pass unchanged for AC7;
  a Playwright test for AC8 confirming cards are present/reachable regardless of scroll
  position and that the reveal effect is suppressed under
  `prefers-reduced-motion: reduce`).

## Designs and attachments
None. No attachments or Figma designs were provided with this ticket; all visual
requirements come from the brief's written description and selected comments.

## Dependencies
- Existing markup and behaviour in `src/App.tsx` (status filter, live result count,
  `TaskList` composition) and `src/components/TaskList.tsx` (task cards, status/priority/due
  line, star button) — the stylesheet is applied to this markup, adding only class names.
- Existing `aria-pressed`, `aria-label` and `aria-live` attributes, which the starred/default
  hover states, focus styling and the new scroll-reveal animation must respect rather than
  replace or hide.
- `src/main.tsx`, which will import the new global stylesheet.
- The "HELLO WORLD" welcome block ships in a separate, not-yet-merged pull request and is
  explicitly out of scope here; no dependency on it is assumed.
- No dependency on other in-flight tickets (`related_work` is empty for this run).

## Assumptions
- The live region text ("Showing X of Y tasks · N starred") and the empty-filter status
  message (`role="status"` in `TaskList.tsx`) are existing page content; they receive the
  same baseline page typography/spacing as the rest of the page but do not need their own
  acceptance criterion beyond general readability and contrast (covered by AC4/AC6).
- "System font stack" means the OS/browser default sans-serif stack (e.g.
  `-apple-system, "Segoe UI", Roboto, sans-serif`) with no web font loading, consistent with
  the "no new dependency" exclusion.
- Exact colour values, spacing scale and badge hues are implementation detail for the plan
  stage, constrained only by AC3 (distinct per status) and AC4 (AA contrast); this
  specification does not mandate specific colours.
- "Hover" state for the star button is a visual-only affordance; it does not need a
  touch/no-hover fallback beyond the existing default and pressed states, since no AC
  requires one.
- "Lazy load to the cards appearing on scroll" (comment 104677, confirmed in scope by
  comment 104680) means a scroll-triggered visual reveal animation (e.g. opacity/transform
  fade-in or slide-in), not literal deferred data loading, pagination or DOM
  virtualization: the task list is a fixed 12-item array with no backend and no loading
  cost to defer, and the ticket's own title asks for an "accessible" result, which requires
  all cards to stay present and reachable in the DOM throughout. This interpretation drove
  AC8. The exact trigger threshold, easing, duration and translate distance for the reveal
  are implementation detail for the plan stage, constrained only by AC8 (content stays
  accessible; motion is reduced for `prefers-reduced-motion: reduce`).
- The scroll-reveal exception to "no animations" (comment 104680) applies only to the card
  reveal itself; it does not reopen animation/transition for other elements (badges, star
  button states, focus outline) unless a future comment says otherwise.
