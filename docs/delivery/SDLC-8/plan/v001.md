# Implementation plan: Style the task list page with a clean, accessible look

> Provenance is added by the coordinator. Implements the approved specification revision named in the provenance.

## Approach
Add one dependency-free global stylesheet (`src/styles.css`), imported once from `src/main.tsx`,
defining colours, spacing and font sizes as CSS custom properties in a single `:root` block.
Apply it to the existing markup in `src/App.tsx` and `src/components/TaskList.tsx` by adding
class names only — the rendered DOM hierarchy (tags, nesting, roles, labels) stays identical to
today's, so none of the existing behavioural tests need to change.

The one exception is AC8 (scroll-triggered reveal): each task card needs its own
`IntersectionObserver` instance, which under the Rules of Hooks requires its own component
instance. `TaskList` is split so each `<li>` is rendered by a small local `TaskCard` component
(not exported, not a new top-level feature) using a new hook, `useRevealOnScroll`. The hook
feature-detects `IntersectionObserver`: where it is unavailable (e.g. jsdom in component tests,
or an unsupporting browser) it marks the card visible immediately, so content is never hidden
from assistive technology and the existing/new component tests never need a browser API mock.
`prefers-reduced-motion: reduce` is handled entirely in CSS (a media query overrides the hidden
state and removes the transition), so no JavaScript media-query handling is needed and the
reduced-motion behaviour is identical whether or not `IntersectionObserver` fired.

Badge colours use the same light-background/dark-text pairings for all three statuses, computed
against WCAG's relative-luminance formula to clear 4.5:1 well before implementation (see
Interfaces and data) so AC4 is a design constant, not a late fix.

## Interfaces and data
- New hook `useRevealOnScroll<T extends Element>(): { ref: RefCallback<T>; isVisible: boolean }`
  in `src/components/useRevealOnScroll.ts`. Pure UI concern (no exported type change, no domain
  impact). Disconnects its observer after the first reveal (reveal-once, not a toggle).
- New local (non-exported) component `TaskCard` inside `src/components/TaskList.tsx`. `TaskList`'s
  exported props (`tasks`, `starred`, `onToggleStar`) are unchanged.
- CSS custom properties defined once in `src/styles.css` `:root`, grouped as colour, spacing and
  font-size tokens, e.g. `--color-bg`, `--color-text`, `--color-border`, `--color-focus`,
  `--color-badge-todo-bg` / `--color-badge-todo-text` (and the `in-progress` / `done` equivalents),
  `--space-1`…`--space-6`, `--font-size-sm`/`--font-size-base`/`--font-size-lg`/`--font-size-xl`,
  `--radius`.
- Badge colour pairs (fixed at plan time so AC4 is provable, not discovered during review),
  verified against the WCAG relative-luminance contrast formula:
  - To do: background `#e2e8f0` / text `#1e293b` → **11.9:1**
  - In progress: background `#fef3c7` / text `#78350f` → **8.1:1**
  - Done: background `#dcfce7` / text `#14532d` → **8.3:1**
  - Base page text `#1a1a1a` on background `#ffffff` → >15:1.
  - Focus outline colour `#2563eb` on white → 5.2:1 (exceeds the 3:1 non-text contrast
    threshold for a visible indicator).
  All comfortably clear the 4.5:1 AA threshold in AC4; the e2e contrast test in
  `e2e/styling.spec.ts` re-verifies this against the real rendered page rather than trusting the
  arithmetic alone.
- No new npm dependency; `IntersectionObserver` and `matchMedia`-free `prefers-reduced-motion`
  (handled in CSS, not JS) are native browser/CSS features, per the constraint in the
  specification and `docs/guardrails.md`.

## Implementation steps
1. Create `src/styles.css` with the `:root` token block, then page/header/controls layout rules
   (centred column, `max-width: 720px`, padding, system font stack), focus-visible rules for
   `select` and `button`, and a base reset for the task `<ul>` (no default list styling).
2. Import it once from `src/main.tsx` (`import "./styles.css";`, before the `createRoot` call).
3. Add class names to `src/App.tsx`'s `<main>`, `<h1>` and the live-region `<p>` (the existing
   `controls` div already has a class to hook the one-line label/select layout onto). No other
   markup change.
4. In `src/components/TaskList.tsx`, extract the existing `<li>` body into a local `TaskCard`
   component that calls `useRevealOnScroll<HTMLLIElement>()`, adds `task-card` (+ a
   `task-card--visible` class once `isVisible`) to the `<li>`, adds `badge badge--<status>` to the
   status `<span>`, and `star-button` (+ `star-button--active` when pressed) to the `<button>`.
   Keep the existing `data-testid`, `aria-pressed`, `aria-label`, text content and element order
   unchanged.
5. Add `src/components/useRevealOnScroll.ts` implementing the ref/observer/fallback described
   above.
6. Add the card, badge, star-button and reveal/reduced-motion CSS rules to `src/styles.css`
   (initial `opacity: 0; transform: translateY(8px); transition: ...` on `.task-card`, `.task-card--visible`
   clearing both, and a `@media (prefers-reduced-motion: reduce)` block that forces the card to
   its final state and removes the transition regardless of the `--visible` class).
7. Write `src/styles.test.ts`, `src/App.styling.test.tsx` and `e2e/styling.spec.ts` per the
   mapping below.
8. Run `npm run lint`, `npm run typecheck`, `npm run test:unit`, `npm run build`, `npm run test:e2e`
   locally; confirm `src/App.test.tsx`, `src/domain/filter.test.ts`, `src/storage/starred.test.ts`
   and `e2e/app.spec.ts` are untouched and still pass.

## Risks
| Risk | Mitigation |
|---|---|
| `src/App.tsx` overlaps with SDLC-7's in-flight change to the same file | Rebase onto `main` after SDLC-7 merges before implementing; keep this ticket's edits to class-name additions only, minimising merge surface |
| Splitting `TaskList` into a `TaskCard` subcomponent could be read as "new component", which the specification's Exclusions restrict | Scope explicitly carves out markup restructuring "as needed to satisfy AC2/AC3/AC8"; the component is local/unexported, not a new top-level feature, and the rendered DOM is unchanged — call this out in the PR description |
| `IntersectionObserver` unavailable in older browsers or jsdom could hide cards or throw | Feature-detect and fall back to immediately visible; this also means component tests need no browser-API mock |
| Chosen badge/text colour pairs could be wrong once rendered for real (fonts/anti-aliasing don't change ratios, but a transcription slip when writing the CSS would) | `e2e/styling.spec.ts` recomputes contrast from the live rendered page, not from this document |
| CSS regressions could unintentionally affect layout enough to break existing Testing Library/Playwright queries that rely on visible text or roles | No `display: none` or content hiding anywhere in the new CSS; existing tests query by role/label, which this plan does not change |

## Rollback implications
Purely additive/presentational: reverting means removing the `src/styles.css` import from
`src/main.tsx`, deleting `src/styles.css` and `src/components/useRevealOnScroll.ts`, and
reverting the class-name/TaskCard-extraction edits in `src/App.tsx` and
`src/components/TaskList.tsx`. No data, storage format or migration is touched, so rollback is a
plain revert with no data cleanup.
